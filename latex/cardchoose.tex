\title{Cardchoose: simple, fast sampling without replacement}
\author{Paul~Crowley}

\begin{document}
\maketitle
\begin{abstract}
    We present Cardchoose, a new algorithm for choosing \(k\) distinct
    natural numbers below \(n\) such that every set of \(k\) is equally
    likely. It draws a multiset of \(k\) values below \(n - k + 1\)
    with a P\'olya urn, then sorts it and converts it to a set by the
    stars and bars bijection. It is a
    few lines of integer arithmetic and a call to a standard sort, needs
    no memory beyond the output array, and takes \(\bigO{k \log k}\)
    time. We benchmark C++ and Rust implementations of it and twelve
    other algorithms over a wide range of \(n\) and \(k\), for both
    sorted and random order output. No algorithm is fastest for every
    \(n\), \(k\), language and output order. Cardchoose is among the
    fastest for sorted output; for random output, algorithms that use a
    hash table are faster until the table outgrows the cache. Among the
    algorithms that need no memory beyond their output, it has the best
    worst-case time per number output over most of the range of \(k\),
    and it is by far the simplest algorithm to perform acceptably
    across the whole range tested. GitHub:
    \url{https://github.com/ciphergoth/sansreplace}
\end{abstract}

\section{Introduction}

Sampling without replacement means choosing \(k\) distinct numbers
from \(\{0, 1, \ldots, n-1\}\) such that every \(k\)-element subset is
equally likely to be returned. Many programming languages include facilities for this in
their standard libraries, for example Python's
\mintinline{python}{random.sample()} or Rust's
\mintinline{rust}{rand::seq::index::sample}; Ting \cite{ting} surveys
the algorithms that several of them use.

We present Cardchoose, a new algorithm for this problem, which we
first proposed in October 2018. It chooses a multiset
with a P\'olya urn and turns it into a set with a sort, in a few lines
of integer arithmetic. It needs
no memory beyond the array in which the result is written, and takes
\(\bigO{k \log k}\) time. \autoref{cardchoose} explains it and proves
it fair, and \autoref{priorart} places it relative to earlier work.
A video \cite{video} explains the algorithm and its proof with
animation. Implementations of every algorithm described here, with the
benchmarks and their results, are at
\url{https://github.com/ciphergoth/sansreplace}.

Many other algorithms solve this problem, with different strengths.
Some are fast only for certain values of \(k, n\), for example where
\(k\) is small or where \(\frac{n}{k}\) is small. Some update a
hash-based data structure such as a set or dictionary for each value
generated, which adds memory and a significant constant factor to the
runtime. Some need extra memory proportional to \(n\), or
floating-point arithmetic. We describe twelve such algorithms in
\autoref{otheralgs}, and in \autoref{benchmarks} we compare the
performance of C++ and Rust implementations of each;
\autoref{notbenchmarked} lists others that we have not timed. Along the way, in
\autoref{quadraticf2}, we describe what appears to be a new way to run
Floyd's permutation algorithm on an array, which keeps the output in a
fair random order without shifting any entries.

No single algorithm is close to the fastest for all \(n, k\), and
libraries such as Python's and Rust's implement several algorithms and
choose between them based on \(n\) and \(k\). In \autoref{choosing},
we find the small sets of algorithms that between them minimise the
worst time per number output. Three algorithms need no extra memory
and always perform reasonably, and of these Cardchoose is by far the
simplest, and with a fast sort the fastest over most of the range.

\section{Cardchoose}\label{cardchoose}

Cardchoose first chooses a multiset uniformly at random, then sorts it
and converts it to a set. A Python implementation follows. It returns
\(k\) distinct integers below \(n\) in sorted order, with every set of
\(k\) equally likely.

\inputminted{Python}{code/cardchoose.py}

Each pass of the first loop takes one random number, one comparison
and one write, with no search, and nothing is stored outside the output
array.

\subsection{Notation}

Let \(\NN_{<n} \defeq \{i \in \NN: i < n\}\), the set of natural
numbers less than \(n\) where \(\NN = \{0, 1, 2, \ldots\}\). Let
\(\binom{S}{k} \defeq \{s \subseteq S: |s| = k\}\), the set of all
\(k\)-element subsets of \(S\).

A \emph{multiset} is an extension of a set in which elements can
appear more than once; we use brackets to delimit the elements of a
multiset, so $[0, 1, 1]$ is the same multiset as $[1, 0, 1]$ but
distinct from $[0, 0, 1]$. Define \(\multichoose{U}{k}\) to be the set
of multisets of cardinality \(k\) whose elements are drawn from
\(U\), and \(\multichoose{n}{k} \defeq
\left|\multichoose{\NN_{<n}}{k}\right|\) the number of such multisets
over \(\NN_{<n}\).

\subsection{Subsets as stars and bars}\label{starsandbars}

The well-known ``stars and bars'' correspondence \cite[Chapter II
\S 5]{feller} is a bijection between \(\binom{\NN_{<n}}{k}\) and
\(\multichoose{\NN_{<t}}{k}\), where \(t = n - k + 1\). Write the
numbers \(0, \ldots, n-1\) in a row, marking each chosen number as a
star and each unchosen one as a bar. For \(n = 7\), \(k = 3\) and the
subset \(\{1, 2, 5\}\):

\begin{displaymath}
    \begin{array}{ c c c c c c c }
        0 & 1 & 2 & 3 & 4 & 5 & 6 \\
        \big| & \star & \star & \big| & \big| & \star & \big| \\
    \end{array}
\end{displaymath}

A row of \(k\) stars and \(n - k\) bars is exactly a \(k\)-element
subset of \(\NN_{<n}\): the stars' positions are the chosen numbers.
Following Feller, think of the spaces between bars, including the
space at each end, as \emph{cells}, and number them from \(0\).
Instead of its position, describe each star by its \emph{cell number},
the number of bars to its left:

\begin{displaymath}
    \begin{array}{ c c c c c c c }
        \big| & \star & \star & \big| & \big| & \star & \big| \\
          & 1 & 1 & & & 3 & \\
    \end{array}
\end{displaymath}

A cell number can be anything from \(0\) (before all the bars) to
\(n - k\) (after all of them), so there are \(t\) cells.
Stars can share a cell, so the stars' cell numbers form a multiset
rather than a set, in \(\multichoose{\NN_{<t}}{k}\). This is the map
from \(\binom{\NN_{<n}}{k}\) to \(\multichoose{\NN_{<t}}{k}\).

A star's position is the number of bars to its left plus the number of
stars to its left. From this we can implement the inverse map: sort
the multiset, which makes each star's index the number of stars to its
left, and add each index to its cell number:

\begin{displaymath}
    \begin{array}{ l c c c }
        \text{sorted cell numbers} & 1 & 1 & 3 \\
        \text{+ index} & 0 & 1 & 2 \\
        \text{positions} & 1 & 2 & 5 \\
    \end{array}
\end{displaymath}

This inversion is the last three lines of the algorithm. What remains
is to choose a multiset in \(\multichoose{\NN_{<t}}{k}\) uniformly at
random.

\subsection{Choosing a multiset fairly}\label{fairmultiset}

Putting each of \(k\) stars in a cell chosen independently from
\(\NN_{<t}\) does not give a uniform multiset. With \(t = 2\), \(k =
2\), the multiset \([0, 1]\) comes up half the time, because it can
arrive as \(0, 1\) or as \(1, 0\), while \([0, 0]\) and \([1, 1]\) get
a quarter each. Independent draws favour variety; we need to favour
repeats, by exactly the right amount.

A standard probability model favours repeats in just this way: the
P\'olya urn \cite[Chapter V \S 2, pp.~119--120]{feller}. Feller's urn
holds balls of two colours; we use its generalisation to \(t\) colours
\cite[\S 2.4]{levinperes}, which starts with \(t\) balls, one of each
colour in \(\NN_{<t}\). Each step draws a ball
uniformly at random, records its colour, and puts it back along with a
new ball of the same colour. A colour drawn \(c\) times so far has \(c
+ 1\) balls in the urn, so it is \(c + 1\) times as likely to be drawn
next as a colour not yet drawn.

The loop in the listing runs exactly this urn, numbering the balls in
the order they enter it: balls \(0, \ldots, t - 1\) are the originals,
ball \(b < t\) having colour \(b\), and ball \(t + i\) is the one added
at step \(i\). At step \(i\) the urn holds \(t + i\) balls, so
\mintinline{python}{randrange(t + i)} draws one. If \(r < t\), it is
an original, of colour \(r\). Otherwise it is the ball added at step
\(r - t\), whose colour is the one drawn at that step,
\mintinline{python}{d[r - t]}.

\subsection{Why the urn is fair}\label{proof}

That the urn draws every multiset in \(\multichoose{\NN_{<t}}{k}\) with
the same probability is a standard lemma \cite[Lemma 2.7]{levinperes};
for completeness, we give two independent proofs.

\paragraph{By counting insertions.} Picture the urn as a process on
the row of \autoref{starsandbars}: starting from the \(t -
1\) bars alone, insert each new star in a uniformly random slot in the
row so far, between two neighbouring symbols or at either end. Before
step \(i\) the row holds \(t - 1\) bars and \(i\) stars, so it has \(t
+ i\) slots, and a cell holding \(c\) stars has \(c + 1\) of them. So
the cell receives the new star with probability \((c + 1) / (t +
i)\), just as the urn draws a colour, and the stars' cell numbers, in
the order they are inserted, have the same distribution as the colours
the urn draws.

Label each star with the step that inserted it, \(0\) to \(k
- 1\). A run is a sequence of slots \(s_0, \ldots, s_{k-1}\) with \(s_i
\in \NN_{<t + i}\), and all \(t (t + 1) \cdots (t + k - 1)\) such
sequences are equally likely. Each run ends in a row of \(t - 1\) bars
and \(k\) labelled stars, and every such row is the end of exactly one
run: deleting star \(k - 1\) recovers the row before the last step, and
the slot \(s_{k-1}\) the star went into, and repeating this recovers
the whole sequence. So every labelled row has the same probability.
Erasing the labels takes exactly \(k!\) labelled rows to each
unlabelled one, so every row of \(t - 1\) bars and \(k\) stars has the
same probability, and with it every multiset of cell numbers.

\paragraph{By calculation.} Consider a run of the urn that draws the
colours \(x_0, \ldots, x_{k-1}\), and let \(c_j\) be the number of
times colour \(j\) appears. At step \(i\) the urn holds \(t + i\)
balls, and one more ball of colour \(x_i\) than the number of earlier
steps that drew \(x_i\). Over the whole run, the numerators for colour \(j\) are
therefore \(1, 2, \ldots, c_j\), and the probability of this sequence
is
\begin{displaymath}
    \frac{\prod_j c_j!}{t (t + 1) \cdots (t + k - 1)}
    = \frac{(t - 1)! \prod_j c_j!}{(t + k - 1)!},
\end{displaymath}
which depends only on the counts, not on their order, as Feller
observes for two colours \cite[pp.~120--121]{feller}. The multiset
with these counts is drawn by \(k! / \prod_j c_j!\) distinct
sequences, so its probability is
\begin{displaymath}
    \frac{k!}{\prod_j c_j!} \cdot \frac{(t - 1)! \prod_j c_j!}{(t + k - 1)!}
    = \frac{k! \, (t - 1)!}{(t + k - 1)!}
    = 1 \Big/ \binom{t + k - 1}{k},
\end{displaymath}
the same for every multiset in \(\multichoose{\NN_{<t}}{k}\).

By \autoref{starsandbars}, converting the multiset then gives every
subset in \(\binom{\NN_{<n}}{k}\) with the same probability.

\subsection{Prior art}\label{priorart}

Physicists have names for the three distributions in this story
\cite[Chapter II \S 5]{feller}. Distinguishable particles placed
independently in cells, the biased way of picking a multiset in
\autoref{fairmultiset}, is Maxwell--Boltzmann statistics.
Indistinguishable particles with every occupancy pattern equally
likely, a uniform multiset, is Bose--Einstein. At most one particle
per cell with every pattern equally likely, a uniform subset, is
Fermi--Dirac. So the one-line summary of Cardchoose is: generate a
Bose--Einstein configuration with a P\'olya urn, then map it to
Fermi--Dirac by stars and bars.

Both halves are long established. The P\'olya urn is a textbook model,
and Niven and Grendar \cite{nivengrendar} map all three statistics onto
it. Uniform counts are also what the scholium of Bayes's
essay \cite{bayes} takes to characterise knowing nothing beforehand,
the assumption behind Laplace's rule of succession \cite[Chapter V \S
2, pp.~123--124]{feller}. For \(t\) outcomes, that rule says that after
\(i\) trials, of which \(c\) came out \(j\), the next comes out \(j\)
with probability \((c + 1) / (t + i)\): exactly the urn's step, so the
urn draws each element of a uniformly random multiset revealed in
random order from its correct distribution given those before it.

We have not found the urn set out as an algorithm, though. Its draws
can be generated from the other side of an equivalence that Blackwell
and MacQueen \cite{blackwellmacqueen} prove for a more general urn:
draw a vector of probabilities from a Dirichlet distribution, then
sample from it independently. That takes floating-point arithmetic and
memory proportional to \(t\). The device in Cardchoose's first loop,
drawing by copying a uniformly random earlier entry of an array, does
appear in Batagelj and Brandes's generator for preferential-attachment
graphs \cite{batageljbrandes}, which runs a related urn where each step
also adds a new colour. The combinatorial generation literature does generate random
multisets, but through stars and bars in the other direction:
Nijenhuis and Wilf's RANCOM \cite[Chapter 6]{nijenhuiswilf} chooses a
random \((k-1)\)-subset of \(\{1, \ldots, n+k-1\}\) and differences
it. Nor do surveys of sampling without replacement describe anything
like Cardchoose: Devroye's \cite[Chapter XII]{devroye} has no urn and
no stars and bars, and Ting's \cite{ting} reworkings of the
established algorithms are a sparse Fisher--Yates sampler, which is
Ernvall and Nevalainen's HSEL \cite{hsel}, the swapping method on an
existing array with its swaps undone afterwards, and a sorted sampler
that draws each skip from a beta-binomial distribution in floating
point. The nearest we have found to drawing first and sorting
afterwards is a sampler that Bentley sketches
\cite[\S 12.3]{pearls}, which draws with replacement, sorts, and
removes duplicates (\autoref{notbenchmarked}).

Five other algorithms need no memory beyond the output array and take
\(\bigO{k}\) expected time: Teuhola and Nevalainen's HTRY
\cite{teuhola}, Nijenhuis and Wilf's RANKSB
\cite[Chapter 4]{nijenhuiswilf}, Ahrens and Dieter's SG*
\cite{ahrensd}, Vitter's Algorithm D and Shekelyan
and Cormode's Hidden Shuffle \cite{hiddenshuffle}. Hidden Shuffle
postdates Cardchoose, and the last three need floating-point arithmetic.
We have not benchmarked HTRY or SG*; \autoref{notbenchmarked} describes
them.

Gupta and Bhattacharjee's GSEL \cite{gupta} also takes
\(\bigO{k \log k}\) time and can return sorted output. Like SELECT, it
draws each value as a uniform rank among the values not yet chosen,
and it finds the value with that rank in a balanced tree of the values
chosen so far, as Ernvall and Nevalainen \cite{hsel} had suggested;
Rouzankin and Voytishek \cite{RouzankinVoytishek} use a sorted array
or an unbalanced search tree instead. We have not benchmarked GSEL:
the tree needs memory that Cardchoose does not, and following pointers
through it for every value drawn is unlikely to beat one sort over a
flat array. Rouzankin and Voytishek's halving algorithm also takes
\(\bigO{k \log k}\) expected time and returns sorted output, with only
a recursion stack beside the output array: it splits the range in two,
decides with one draw for each value which half it falls in, and
recurses, so it makes about \(\log k\) draws for each value where
Cardchoose makes one.

\section{Other algorithms}\label{otheralgs}
We compare Cardchoose with twelve other algorithms. Every
implementation fills an array of \(k\)
elements. Some applications require that the returned elements be in
sorted order, while others need the order of the elements to be a fair
random draw. Both Python's \mintinline{python}{random.sample()} and
Rust's \mintinline{rust}{rand::seq::index::sample} return in a fair
random order.

An algorithm that returns one order can be made to return the other
with a sort or a Fisher--Yates shuffle. But each algorithm returns one
order naturally, and the other costs that extra step, so which
algorithm is fastest can depend on which order the caller wants. In
our benchmarks we time both a sorted and a random variant of every
algorithm.

For each algorithm we give how it works, the order it returns, its
expected time, and any memory it needs beyond the output array.
All but two draw only random integers below a bound;
Vitter's Algorithm D and Hidden Shuffle also need floating-point
arithmetic.

    \begin{tabular}{l|l|l|l|l}
    Algorithm & Time & Order & Extra memory & Floats \\
    \hline

\subsection{Quadratic rejection sampling}
\inputminted{Python}{code/quadraticreject.py}
Draw a value below \(n\), check whether it is already in the output by
scanning the output so far, and append it if not; repeat until the
output has \(k\) values. The output is in random order and no extra
memory is needed. Each check takes \(\bigO{k}\) time, so the whole
takes \(\bigO{k^2}\) expected time for \(k \leq n/2\), and more as
\(k\) approaches \(n\) and more draws are rejected, as for set-based
rejection sampling below.

\subsection{Set-based rejection sampling}
\inputminted{Python}{code/rejectionsample.py}
As above, but check each draw against a set of the values chosen so
far, with an efficient membership test. Fan, Muller and Rezucha
\cite[Method 5]{fanetal} keep the set in a table in sorted order;
Knuth \cite[\S 3.4.2, exercise 16]{taocp2}, Teuhola and Nevalainen
\cite{teuhola} and Ahrens and Dieter
\cite{ahrensd} keep it in a hash table, and Devroye \cite[Chapter XII \S 2]{devroye}
compares the data structures that can hold it. The output is in random
order, and the set takes \(\bigO{k}\) memory. With a hash table, this
takes \(\bigO{k}\) expected time for \(k \leq n/2\), where each draw is
rejected with probability at most a half; Jakobsson \cite{jakobsson}
shows that the expected number of draws is then less than
\(2k \ln 2 \approx 1.39k\). As \(k\) approaches \(n\), rejections
mount, as in the coupon collector's problem \cite[Chapter IX \S 3,
pp.~224--225]{feller}: the expected number of draws is \(n(H_n - H_{n-k})\)
\cite[\S 6.3, p.~300]{goodman}, where \(H_m\) is the \(m\)th harmonic
number, so at \(k = n\) it takes
\(\bigO{n \log n}\) time.

\subsection{Floyd's F2}
\inputminted{Python}{code/floydf2.py}
Build a set of the values chosen so far, one value per step, with no
rejection \cite{floydf2}. Before the step for \(m\), running from
\(n - k\) to \(n - 1\), the set is a uniformly random subset of
\(\NN_{<m}\). Draw \(j\) uniformly from \(\NN_{<m + 1}\), and add
\(j\) if it is not in the set, or \(m\) if it is; \(m\) is never in the
set before its own step, so the set grows by one, and it is then a
uniformly random subset of \(\NN_{<m + 1}\). This makes exactly \(k\)
draws and takes \(\bigO{k}\) expected time with a hash set, which
takes \(\bigO{k}\) memory, and the result has no order. For random
order output, our C++ and Rust implementations do not shuffle
afterwards. Instead, as in Ting's random-order version of Floyd's
algorithm \cite{tingblog}, when the chosen value is already present,
they move a randomly chosen earlier output to the end and put the new
value in its place. This keeps the order uniformly random, and costs an
extra random number only on collisions. Floyd's own Algorithm P
\cite{floydf2} needs no extra draw, but it has to find the matching
entry in the output, which a set does not record.

\subsection{Quadratic F2}\label{quadraticf2}
\inputminted{Python}{code/quadraticf2.py}
Floyd's F2 with the output array as its set, scanned to check each
draw, so that it needs no extra memory and takes \(\bigO{k^2}\) time.
For random order, Floyd's Algorithm P \cite{floydf2} needs no shuffle
and no extra draw: a new draw goes on the front of the output, and
when the draw is already present, \(m\) is inserted just after it. In
an array, that insertion shifts every entry after it, taking time
proportional to their number on each collision. Our version instead
replaces the matching entry with \(m\) and appends the draw \(r\), so
that nothing is shifted; the scan has already found where \(r\) is. As
with Algorithm P, each step can be undone, so every ordered output
comes from exactly one sequence of draws, and all are equally likely.
Rust's \mintinline{rust}{rand} crate also used
Floyd's F2 with a scan of the output \cite{rust-random}: for
\(k < 50\) it ran Algorithm P in mirror image, appending each new draw
and inserting \(m\) before the matching entry, and for larger \(k\) it
shuffled the whole output afterwards, which costs \(k\) more draws. It has used our version
since 2023; the pull request that made that change \cite{randpr} is
the first publication of it that we know of. For sorted output,
our implementations append \(m\) instead, since before the sort only
the set matters, and then sort.

\subsection{Bit-vector F2}
\inputminted{Python}{code/bitvectorf2.py}
Floyd's F2 with a bit vector of \(n\) bits as its set. Teuhola and
Nevalainen \cite{teuhola} and Devroye \cite[Chapter XII \S 2]{devroye}
describe a bit vector as the set for rejection sampling; Bentley
\cite[Column 13]{pearls} times one, and sets Floyd's algorithm with
the same sets as an exercise. In our benchmarks it is the fastest
algorithm where \(n/k\) is moderate (\autoref{results}). For sorted
output, scan the bit vector afterwards and write out the position of
every bit that is set, as Bentley does there and in his bit-vector
sort \cite[Column 1]{pearls}, so that no sort is needed. For random output, there is no scan, and the order is kept
random as in Floyd's F2 above. The listing uses a byte for each bit,
for clarity; our C++ and Rust implementations take a packed bit vector
from a library, Boost's \mintinline{cpp}{dynamic_bitset} and the
\mintinline{rust}{fixedbitset} crate, which hold 64 bits in a word and
find the set bits by counting trailing zeros. The draws
take \(\bigO{k}\) time, but clearing the bit vector, and for sorted
output scanning it, takes \(\bigO{n}\) time, though little for each
value, since a word covers 64 of them.

\subsection{Iterative choosing (Algorithm S)}
\inputminted{Python}{code/iterativechoose.py}
Go through the values of \(\NN_{<n}\) in order, and choose each with
the probability that it is in the sample given how many values are
still to choose and how many remain to consider
\cite[Method 1, p.~391]{fanetal}; this is Knuth's Algorithm S
\cite[\S 3.4.2]{taocp2}, which he reports T.~G.~Jones found
independently. The output is sorted, no extra memory is needed, and it
makes one draw for every value it considers, so it takes \(\bigO{n}\)
time.

\subsection{Reservoir sampling (Algorithm R)}
\inputminted{Python}{code/reservoirsample.py}
Fill the output with the elements of \(\NN_{<k}\) in random order.
Then for each \(i\) from \(k\) to \(n - 1\), draw \(r\) from
\(\NN_{<i + 1}\), and if \(r < k\), replace the \(r\)th output with
\(i\); this is Knuth's Algorithm R \cite[\S 3.4.2]{taocp2}, which he
credits to Alan Waterman. The output is in
random order, no extra memory is needed, and it makes one draw for
every value, so it takes \(\bigO{n}\) time. Vitter's Algorithm Z
\cite{vitterZ} skips ahead instead of considering every value, but it
is for input whose length is not known in advance; where \(n\) is
known, his Algorithm D does less work.

\subsection{SELECT}
\inputminted{Python}{code/select.py}
Fill an array with the elements of \(\NN_{<n}\), and run the first
\(k\) steps of a Fisher--Yates shuffle on it: at step \(i\), swap a
random element from position \(i\) onwards into position \(i\)
\cite[\S 6.3, p.~303]{goodman}. The first \(k\) elements are then the
sample, in
random order. It makes only \(k\) draws, but the array takes
\(\bigO{n}\) memory and \(\bigO{n}\) time to fill.

\subsection{HSEL}
\inputminted{Python}{code/hsel.py}
SELECT with a ``virtual'' array: a hash table stores only the elements
that have changed, so it needs no \(n\)-element array
\cite{hsel}. The output is in random order, and it takes \(\bigO{k}\)
expected time and \(\bigO{k}\) memory for the hash table. An algorithm
of Ole-Johan Dahl's does the same job. It is an exercise in Knuth
\cite[\S 3.4.2, exercise 15]{taocp2}, and was already in the second
edition of 1981, a year before Ernvall and Nevalainen's paper appeared.
Dahl keeps the entries for the output positions in an array beside the
output, and looks up only the others in a symbol table. Our C++ and
Rust implementations use a simpler and faster form of the same idea,
in which the output array itself holds those entries, so that only
swaps that reach beyond them touch the hash table. This form was
described by rici \cite{rici}; we thank Mathias Weller for bringing it
to our attention.

\subsection{RANKSB}
Divide \(\NN_{<n}\) into \(k\) bins of nearly equal size. First
decide how many of the chosen values fall in each bin, by simulating
set-based rejection sampling while keeping only a count for each bin:
a draw is rejected with the probability that it would duplicate a value
already accepted in its bin, which depends only on that bin's count.
Then choose that many values within each bin; bins hold about one value
each, so a quadratic method suffices. The output is sorted, the expected
time is \(\bigO{k}\) for \(k \leq n/2\), and the program in
\cite[Chapter 4]{nijenhuiswilf} needs no memory beyond the output
array. Our \repo{cpp/ranksb.cpp}{C++} and
\repo{rust/src/algorithms/ranksb.rs}{Rust} implementations follow that
program, except that they fill each bin as soon as they know where its
values go, rather than first marking out every bin's slots and then
scanning for the marks; our \repo{python/algorithms/ranksb.py}{Python}
implementation keeps the counts in a separate array, which is easier to
follow.

\subsection{Vitter's Algorithm D}
Like iterative choosing, produce the output in sorted order, but
instead of deciding about each value in turn, draw the number of values
to skip before the next chosen one directly. The skip has a known
discrete distribution, which Algorithm D samples by rejection from a
continuous approximation, the smallest of \(k\) uniform reals, which can
be drawn in one step, in \(\bigO{1}\) expected time per
output, at the cost of a few floating-point exponentiations, and with
no extra memory. Once \(n \leq 13k\) it falls back on Vitter's
Algorithm A, which draws each skip in time proportional to its length.
Vitter introduced Algorithm D in \cite{vitterfaster}; our
\impls{vitterd} implementations follow the improved code in the appendix of
\cite{vitterD}, which is too long to list here.

\subsection{Hidden Shuffle}
Shekelyan and Cormode's Hidden Shuffle \cite{hiddenshuffle} considers
a Fisher--Yates shuffle of \(\NN_{<n}\) that stops after \(k\) steps,
so that the sample is whatever ends up in the first \(k\) positions;
call these the low positions, and the rest the high positions. Each
step reaches a high position independently, with known probability,
and which high position it reaches is uniform and independent of
everything else. So first count the steps that reach a high position,
then draw that many high positions with replacement in sorted order as
in \cite{bentleysaxe}. The first draw of a high position adds its value
to the sample; a repeat finds a low value swapped there earlier, so the
sample gains a low value instead, much as a collision in Floyd's F2
adds a different value. Given their number, the low values are a
uniformly random subset of the low positions, chosen in order by
Vitter's Algorithm A. The output is sorted, the time is \(\bigO{k}\) in
the worst case, and no extra memory is needed; like Algorithm D, it
relies on floating-point arithmetic, with an exponentiation for each
high draw. The code printed in the proceedings
\cite{hiddenshuffleproc} can divide by zero, and its last step has an
off-by-one error that biases the output; the authors' corrected version
and the errata in \cite{sampleiterator} fix both, and our
\impls{hiddenshuffle} implementations apply those corrections. We thank metasj for bringing this algorithm to
our attention.

\subsection{Cardchoose}
Described in \autoref{cardchoose}: choose a multiset of \(k\) cell
numbers below \(n - k + 1\) with a P\'olya urn, then sort it and add
each one's index to turn it into a set. The output is sorted, and the
only memory needed is the output array.

\subsection{Algorithms not benchmarked}\label{notbenchmarked}
The literature holds many more algorithms than the thirteen we time,
and our coverage is not complete. These are the ones we know of and
have not timed; for some we give a reason, and for others there is
none beyond the size of the list.

\begin{itemize}
\item Ahrens and Dieter's SG, SG* and SH \cite{ahrensd}, all for
sorted output. SG takes each value independently with probability a
little over \(k/n\), drawing the gaps between them from a geometric
distribution in floating point; it starts again if it has fewer than
\(k\) values, and otherwise discards the excess at random. It needs an
array a little longer than \(k\). SG* needs none: it runs the
generator once to count the values, restores its state, and runs it
again, keeping exactly \(k\) by iterative choosing. SH is rejection
sampling into a hash table whose hash is the value scaled down, so
that the table is nearly in order and an insertion sort finishes the
job. Their authors found SG and SH about equally fast, and four to
five times as fast as the Algorithm D of the time.
\item Teuhola and Nevalainen's HTRY \cite{teuhola} is set-based
rejection sampling with its hash table packed into the output array,
each entry holding a value and a link, so that it needs no memory
beyond the output. The packing is intricate, and in its authors' own
timings it takes two to three times as long as their other hash-based
algorithm until \(k\) exceeds \(n/2\) \cite[Figure 4]{teuhola}.
\item Teuhola and Nevalainen's version of HSEL \cite{teuhola} needs
\(2k\) storage locations rather than about \(5k\). It draws all \(k\)
random numbers first and then works out which value each one stands
for, from the last back.
\item Gupta and Bhattacharjee's GSEL \cite{gupta}, and Rouzankin and
Voytishek's algorithms that hold the chosen values in a sorted array
or an unbalanced search tree \cite{RouzankinVoytishek}, draw each
value as a rank among those not yet chosen (\autoref{priorart}). They
need memory that Cardchoose does not, and GSEL follows pointers
through a tree for every value drawn.
\item Rouzankin and Voytishek's halving algorithm
\cite{RouzankinVoytishek} makes about \(\log k\) draws for each value
(\autoref{priorart}).
\item Other ways to draw the skips of a sequential sampler such as
Algorithm D. Devroye \cite[Chapter XII \S\S 3--4]{devroye} gives
several, and oversampling, which rounds sorted uniforms to integers
and repairs the repeats afterwards. Ting \cite{ting} observes that the
skip is a beta-binomial variate, so that the loop takes only a few
lines wherever a library provides a binomial generator; it takes
\(\bigO{k}\) time when that generator takes constant expected time,
and the work of Algorithm D's rejection step is then done inside it.
Like Algorithm D, these draw their skips in floating point.
\item Drawing with replacement, sorting and removing duplicates.
Bentley \cite[\S 12.3]{pearls} suggests drawing somewhat more than
\(k\) values, sorting them, removing the duplicates, and taking a
sorted sample of \(k\) from what is left. It needs room for the excess,
and a second sampler to trim it.
\end{itemize}

\section{Benchmarks}\label{benchmarks}

The accompanying repository includes C++ and Rust
implementations of these algorithms, which were benchmarked for a
variety of values of \(n\) and \(k\), for both sorted output and
random output, on an AWS r8a.xlarge, whose four vCPUs are each a whole
physical core, so nothing shares the core a benchmark runs on:

\begin{itemize}
    \item CPU: AMD EPYC 9R45, four cores
    \item Cache: 48kiB L1 data and 1MiB L2 per core, 16MiB L3 shared
    \item Memory: 32GiB
    \item OS: NixOS 25.11, Linux 6.12
    \item C++ compiler: clang 21.1 with libstdc++ 15 and Boost 1.91,
    \verb|-O3 -march=x86-64-v3|
    \item Rust compiler: rustc 1.98, release profile with one codegen
    unit and link-time optimisation, \verb|-C target-cpu=x86-64-v3|
\end{itemize}

We tested values of \(n\) and \(k\) that are Fibonacci numbers, with
\(n\) up to 701,408,733 (the 44th Fibonacci number) and \(k\) up to
102,334,155 (the 40th).

\subsection{Method}

A Python harness times each point, one algorithm at one \(n\) and
\(k\), in a process of its own: a C++ or Rust program that it starts
afresh for that point, so that a point's time does not depend on what
was timed before it. The process times batches of calls. It doubles the
calls in a batch until a batch takes 5\,ms, then times batches of that
size until it has timed at least three, over at least 0.05 seconds, and
takes the time per call of the fastest batch. It does this with its
stack at each of four positions (see \autoref{pitfalls}), and the
point's time is the fastest of the four; a point where one call takes
0.05 seconds or more is timed at one position, and one where a call
takes a second or more by that call alone. Every batch reseeds the
random number generator from its point alone, with the C++ and Rust
generators in the same state, so every batch at a point makes the same
draws, in any run; the hash tables in both languages hash with a fixed
seed. Every call writes to the same output array, allocated outside the
timing, aligned to a 64-byte cache line and zeroed. Each process runs
with address space randomisation off and an empty environment, pinned
to a core that the kernel keeps other work off. The overhead of a call,
measured by timing a function that does nothing, is about 1.1\,ns, and
is not subtracted. With each point the harness records five of the
processor's performance counters, among them the instructions executed,
which do not change from run to run; so when a time does, the counters
say whether the processor did different work or the same work more
slowly.

The same harness also times the operations the algorithms are built
from, at \(n = 2^{32} - 1\): drawing \(k\) random numbers alone, and
drawing them and then sorting them, shuffling them, or inserting them
into a hash set, so that the difference is the cost of that operation
(\autoref{componenttimes}). We ran the whole benchmark three times, on
separate boots of the machine, and report the fastest of the three
times at each point.

A time depends on more than the algorithm: on where code, data and the
stack happen to lie, on what the compiler and the libraries do, and on
the state of the processor. \autoref{pitfalls} describes the effects we
found, each of which moved some algorithm's time by 10\% or more, and
what we did about each. What remains limits how the results should be
read. At 97.9\% of the 52,561 points timed in all three runs, a second
run came within 5\% of the time we report, and at 99.3\% within 10\%;
we would not read anything into a difference of less than 5\% between
two algorithms at a point, nor less than 10\% where \(k\) is in the
millions. Where an algorithm's time goes on one tight inner loop, as
for the quadratic algorithms, a difference of up to about 15\% may come
from where the compiler happened to place the loop. And SELECT's times
are the least certain: the fill it begins with runs at either of two
speeds, 1.3 times apart, depending on what the processor's prefetcher
does.

\subsection{The two languages}

The C++ and Rust implementations are the same algorithms, written the
same way, from widely used components: the Rust uses its standard
library, with the foldhash crate's hasher for its hash tables, and the
C++ takes its sort and hash tables from Boost, whose flat hash tables
and pattern-defeating quicksort are faster than the standard library's
node-based tables and introsort. Even so, some of these components
differ a great deal.

\paragraph{Hash tables.} Boost's
\mintinline{cpp}{boost::unordered_flat_set} and
\mintinline{cpp}{boost::unordered_flat_map} and Rust's
\mintinline{rust}{HashSet} and \mintinline{rust}{HashMap} are all flat
open-addressing tables that probe a group of slots at once with vector
instructions. Rust's tables by default hash with SipHash, which resists
collision attacks; Boost's do not, and so that the two are comparable
the Rust's hash with foldhash, with a fixed seed, which does not either. Inserting into
the set takes 1.0 to 1.3 times as long in Rust as in C++
(\autoref{componenttimes}), and with random output the hash-based
algorithms take 1.08 to 1.14 times as long at the median.

\paragraph{Sorting.} Boost's \mintinline{cpp}{pdqsort} is a
pattern-defeating quicksort, and Rust's \mintinline{rust}{sort_unstable}
is ipnsort, its successor. Sorting the same arrays of random numbers,
\mintinline{cpp}{pdqsort} takes 1.96 to 2.4 times as long
(\autoref{componenttimes}), and Cardchoose takes about 0.5 times as
long in Rust as in C++. RANKSB, Algorithm D and Hidden Shuffle need
neither a hash table nor a sort, and take about the same time in both
languages for sorted output.

\paragraph{Random numbers.} Both use the Xoshiro256++ generator, and
both turn its output into a number below a bound with a
multiplication. But the C++ uses its own code for this, which takes two
32-bit numbers from each 64-bit output, while the
\mintinline{rust}{rand} crate's \mintinline{rust}{random_range} uses a
whole output for each. Both correct the multiplication's slight bias,
differently: the C++ uses Lemire's method, which rejects the few draws
that cause it and so is exact, and \mintinline{rust}{random_range}
Canon's method, which never rejects and leaves a bias of at most 1 in
\(2^{96}\), too small to detect. The shuffle that turns the sorted output of
RANKSB, Algorithm D and Hidden Shuffle into random order is the same
loop in both languages, but costs 1.3 to 1.5 times as much per number
in Rust (\autoref{componenttimes}); so for random
output, Algorithm D and Hidden Shuffle take 5--8\% longer in Rust at
the median. The \mintinline{rust}{rand} crate's own
\mintinline{rust}{SliceRandom::shuffle} is slower than our loop.

\paragraph{Searching an array.} The quadratic algorithms search the
output so far on every draw. The Rust uses
\mintinline{rust}{slice::contains}, and the C++ a loop of its own that
checks every entry rather than stopping at the first match, so that the
compiler vectorises it.

\paragraph{Bit vectors.} The bit-vector F2 takes its bit vector from
Boost's \mintinline{cpp}{dynamic_bitset} in C++ and the
\mintinline{rust}{fixedbitset} crate in Rust. Setting a bit costs about
the same in both, but the sorted variant reads its output off the
vector, and Boost's \mintinline{cpp}{find_next} starts again from the
position it is given for every number, where
\mintinline{rust}{fixedbitset} works through each word in turn. At
\(n = k = 1{,}346{,}269\), the C++ sorted variant takes 3.8\,ns per
number, against 2.2\,ns with a loop of our own that did the same.

No algorithm is the fastest for all \(n, k\). Quadratic rejection
and quadratic F2 are the fastest for small \(k\), SELECT, reservoir
sampling and iterative choosing for small \(n/k\), and the bit-vector
F2 for moderate \(n/k\), but each of these is very slow elsewhere. The
other algorithms run in \(\bigO{k}\) or \(\bigO{k \log k}\) time, and
differ by smaller factors.

For sorted output, the bit-vector F2 is the fastest algorithm in both
languages wherever \(2k \leq n < 16k\) and \(k < 10^7\). For larger
\(n/k\) the languages differ. In C++, Hidden Shuffle is the fastest
wherever \(n \geq 256k\) and \(k \geq 100\), and wherever
\(n \geq 16k\) and \(k \geq 1000\), Cardchoose takes 1.3 to 2.3 times
as long as Hidden Shuffle. In Rust, Cardchoose is the fastest wherever
\(n \geq 256k\) and \(k < 1000\), and the fastest or within 14\% of it
wherever \(n \geq 256k\); wherever \(n \geq 16k\) and \(k \geq 1000\),
it takes 0.63 to 1.27 times as long as Hidden Shuffle, which is the
faster of the two only for the largest \(k\). Hidden Shuffle takes
about the same time in both languages, so the difference is in
Cardchoose, and in its sort (\autoref{componenttimes}). Hidden Shuffle
is also faster than RANKSB wherever \(n \geq 16k\) and \(k \geq 1000\)
in both languages, with RANKSB taking 1.1 to 2.7 times as long. As
\(k\) approaches \(n\), RANKSB slows down, taking up to 490 times as
long as the fastest algorithm at \(k = n\) in C++, and 940 times in
Rust. Vitter's
Algorithm D, with its fallback to Algorithm A, takes 0.38 to 2.0 times
as long as Hidden Shuffle at every point with \(k \geq 10\). Where
\(n \geq 4k\), it takes 0.63 to 2.8 times as long as Cardchoose in C++
and 0.91 to 5.2 times as long in Rust; where \(n < 2k\) and
\(k \geq 10^5\), it is faster than Cardchoose in both.

For random output, the same algorithms win the same regions in both
languages. SELECT is the fastest algorithm wherever \(2k \leq n < 16k\)
and \(k < 10^5\). From \(n\) of about 8 million, its array is large
enough that glibc's \mintinline{c}{malloc} maps it afresh on every
call, and faulting its pages in again makes it up to 7.9 times slower
than the bit-vector F2, which is the fastest at most of the points
with larger \(k\) there, and at most of those with
\(16k \leq n < 256k\): 151 of 177 in C++, and 134 in Rust. For larger
\(n/k\), quadratic rejection is the fastest or within 5\% of it
wherever \(k < 100\) and \(n \geq 65{,}536k\); and where
\(k \geq 100\) and \(n \geq 256k\), set-based rejection sampling is the
fastest at 145 of the 231 points in C++ and 143 in Rust, and the
bit-vector F2 at most of the rest. Floyd's F2 takes at most 1.23 times
as long as set-based rejection there, and HSEL up to 2.5 times; but
set-based rejection slows down as \(k\) approaches \(n\), and HSEL does
not.

Several of these algorithms slow down as \(k\) approaches \(n\). A
reasonable fix is to switch algorithm there: to iterative choosing for
sorted output, as Nijenhuis and Wilf
\cite[Chapter 4]{nijenhuiswilf} suggest for \(k \geq n/2\), or to
reservoir sampling or SELECT for random output. Another
suggestion, made by Ernvall and Nevalainen \cite{hsel} and by Knuth
\cite[\S 3.4.2, exercise 16]{taocp2}, is to
sample the values to leave out; but that is complicated to do in place,
as Teuhola and Nevalainen \cite{teuhola} found, gives its output in
sorted order, and is unlikely to be faster than switching to one of
the algorithms above. We time each algorithm as described, without any
such switch.

The hash-based algorithms are faster than Cardchoose until their tables
no longer fit in cache. Wherever \(100 \leq k < 10^6\) and
\(n \geq 2k\), set-based rejection, Floyd's F2 and HSEL each take 0.17
to 0.47 times as long as Cardchoose in C++, and 0.35 to 0.89 times as
long in Rust, where Cardchoose's sort is faster. Wherever
\(k \geq 10^7\) and \(n \geq 2k\), Cardchoose is the faster: they take
1.05 to 1.7 times as long in C++, and 1.3 to 2.6 times as long in Rust.
So although in theory their \(\bigO{k}\) time should eventually beat
Cardchoose's \(\bigO{k \log k}\), at the sizes we tested the opposite
happens. In C++, Hidden Shuffle followed by a shuffle takes 0.48 to
0.78 times as long as Cardchoose wherever \(n \geq 16k\) and
\(k \geq 1000\); in Rust, 0.90 to 1.52 times. For very large \(k\), a
parallel algorithm \cite{rajan, sandersetal} should generally be used;
that of Sanders et al.\ calls a sequential algorithm at the leaves of
the parallel tree it builds.

\section{Choosing algorithms}\label{choosing}

We score each algorithm by its worst time per number output in each
decade of \(k\): for each band, the most its time per call divided by
\(k\) reaches at any point with \(k\) in the band, over every \(n\)
tested. This says what it costs at worst, per number, for any \(n\)
and any \(k\) in that range. The bands start at \(k = 10\), 100,
1,000 and so on, the last running from \(10^7\) to the largest \(k\)
tested; below 10, per-call overhead swamps everything. Each band also
has a floor: the score of choosing the fastest of all thirteen
algorithms separately at every point, which no algorithm or set of
algorithms can beat. We give worst cases rather than averages, since
any average depends on which values of \(n\) and \(k\) we chose to
test, and score each band of \(k\) separately since otherwise the
largest \(k\), where everything is slowest per number, would decide
every ranking.

\autoref{bandscpprandom} to \autoref{bandsrustsorted} give, for each
band, the best algorithm, with any within 3\% of it, which is within
the noise between runs, marked \(\approx\); where any of those needs floating point
(Hidden Shuffle and Algorithm D), the best algorithm that does not;
then Cardchoose, and the floor. Each algorithm was timed only until a
call took more than 30 seconds; only the quadratic algorithms reached
that, from \(k = 1.3 \times 10^6\).

Three algorithms are never far from the fastest per number output at

With sorted output, Cardchoose is the best algorithm at every \(k\)
below \(10^7\) in Rust, and the bit-vector F2 above that; in C++,

quadratic algorithms, iterative choosing, reservoir sampling, RANKSB,
Algorithm D, Hidden Shuffle and Cardchoose. Among these, Cardchoose is
the best in 18 of the 28 bands of the four cases: in Rust, every band
from 100 with random output and every band below \(10^7\) with sorted
output, and in C++, every band below \(10^5\) with sorted output and
those from 1,000 to \(10^5\) with random output. Quadratic F2 is the
best in three bands of random output at small \(k\), and Hidden Shuffle
in the other seven, at large \(k\). Among those of the eight that also
need no floating point, Cardchoose is the best in every band but those
three.

An algorithm is dominated by bands if another scores no worse in any
band and better in at least one. Eight algorithms are dominated by
bands in every case: Cardchoose dominates six of them in every case,
quadratic rejection, set-based rejection, RANKSB, iterative choosing,
reservoir sampling and SELECT, HSEL dominates Floyd's F2, and Hidden
Shuffle dominates Algorithm D. Because a band's score is
the worst over every \(n\), that does not make them useless: iterative
choosing, reservoir sampling and SELECT are among the fastest where
\(n/k\) is small, and iterative choosing belongs to the best sets for
sorted output below.

\autoref{cover} shows, for each language and
order, the best set of one, two or three algorithms, if each point uses
the fastest algorithm in the set. A set's score in a band is its worst
time per number output there, as for a single algorithm, and the table
gives the most that exceeds the band's floor, as a ratio, in the set's
worst band: \(1.00\times\) means the set is as good as all thirteen
algorithms together in every band. It also gives the most each set is
slower than the best set of three, in time per number, in any band.
Where the best set needs floating point, it also gives the best set
that does not, or says that a third such algorithm is no better than
two. This assumes the best choice is made at every point; an
implementation has to choose by a rule, such as thresholds on \(k\)
and \(n/k\).

The bit-vector F2 belongs to the best pair in three of the four cases,

three algorithms are as good as all thirteen together, or within 1\% of
it; for random output, no three come within 30\%.

If an implementation has only one algorithm, Cardchoose is a good
choice. By ratio to the floor it is the best single algorithm for
sorted output in Rust, and within 0.03 of Hidden Shuffle for sorted
output in C++; for random output HSEL has the better worst ratio, 2.51
against 4.49 in C++ and 2.14 against 2.49 in Rust. But those ratios are
at their largest where calls are cheap. In time per number, Cardchoose
alone is never more than 6 to 20\,ns slower than the best three
algorithms together, in any case and at any \(k\), where HSEL alone is
up to 27\,ns slower in C++ and 15\,ns in Rust, at large \(k\); and
Cardchoose needs no memory beyond its output. Its largest ratios to the
floor are 4.49 in C++ with random output, for \(10^4 \leq k < 10^5\),
where the hash-based algorithms are at their best, and 2.49 in Rust,
for \(k < 100\), where quadratic F2 needs neither a sort nor a shuffle
and no call to Cardchoose takes more than 1.4\,\textmu s. With sorted
output, they are 2.28 in C++ and 1.53 in Rust, both for
\(k \geq 10^7\).

\section{Benchmarking pitfalls}\label{pitfalls}

Again and again while preparing these results, an odd result, such as
one algorithm faster than another in one language but slower in the
other, or a point whose time changed between runs, came from how it was
measured rather than from the algorithm. Each of the effects below
moved some algorithm's time by 10\% or more while its source code stayed
the same, which is more than many of the gaps between algorithms that
we might otherwise have reported. We describe them at some length,
since a reader comparing algorithms of their own is likely to meet the
same ones;
\repo{measurement.md}{\texttt{measurement.md}}
in the repository has the remaining detail.

\paragraph{The machine.} One of the machine's four cores is kept for
the timing: the kernel is booted with
\verb|isolcpus=3 nohz_full=3 rcu_nocbs=3|, so that it schedules nothing
else there, sends it no timer ticks while one process runs, and does
its own housekeeping on the other cores. Transparent huge pages are
off. The machine is stopped between runs, and may come back on a
different host. It is a virtual machine, which limits what we can look
at: it offers five performance counters at a time, none of them for the
level-3 cache, and no way to turn the processor's prefetchers off.

\paragraph{Where code lands.} Where a function starts within its
64-byte cache line depends on all the code linked before it, and that
alone moved the times of tight loops whose machine code had not
changed: C++ iterative choosing took 15\% longer when a change to the
standard library moved the code before it, and the Rust bit-vector F2's
scan took up to 1.7 times as long when a change to how the Rust was
built did. This is a kind of measurement bias that \textcite{mytkowicz}
describe in general. Both languages now start every function on a cache
line, which makes the timings stable when unrelated code changes, but
not optimal, since a loop's alignment still depends on the code before
it in its own function; so differences of up to about 15\% between
algorithms dominated by a tight inner loop should not be read as
meaningful.

\paragraph{Where data lands.} \mintinline{c}{malloc} promises only
16-byte alignment, so whether an array starts on a cache line depends on
what was allocated before it, and a misaligned start makes about half
the vector loads and stores that sweep it straddle two cache lines. In
Rust, SELECT's fill of its \(n\)-element array took 1.5 times as long
when the array started 16 bytes past a 32-byte boundary, which varied
with where earlier allocations had left it; and C++ quadratic F2, which
scans its own output on every draw, took 1,897\,ns per number at
\(k = 121{,}393\) with the output array where \mintinline{c}{malloc}
put it, and 1,290\,ns with it on a cache line. The array that SELECT
sweeps, and the output array, are now aligned to a cache line.

\paragraph{Where the stack lands.} Where a process's stack starts
depends on the kernel's randomisation of its address space and on the
total length of its environment variables, which sit above it;
\textcite{mytkowicz} found the size of the environment changing which
of two builds looked faster. Here, 20 processes that each timed C++ HSEL
at \(k = 1\) spread over a factor of 1.72 with randomisation on, and
all came within 2\% of the fastest with it off. With it off, padding
the environment by 0 to 4,080 bytes in steps of 16 moved the same
point's time by up to 6\% in a pattern that repeats every 64 bytes, so
with the stack's position within a cache line; at a few sizes it took
1.3 to 1.7 times as long, and at one of the 256, HSEL with \(k = 0\),
which returns at once, took 8.4 times as long. So each process runs with randomisation
off and an empty environment, and times on a stack of its own at four
positions 16 bytes apart, which covers the pattern, and we take the
fastest. This gives every algorithm its best alignment, rather than
whichever one a launch happened to give it.

\paragraph{What the compiler decides.} The \mintinline{rust}{rand}
crate's \mintinline{rust}{random_range} is not marked
\mintinline{rust}{#[inline]}, and once it had several callers, LLVM kept
it out of line for inclusive ranges: sorted reservoir sampling took
1.73\,ns per value of \(n\), against 0.90\,ns with the draw inlined and
0.91\,ns in C++. An early timing program for the Rust hashed strings
for its own purposes, and with those extra callers LLVM kept the hash
function out of line in the algorithms too: set-based rejection,
Floyd's F2 and HSEL took 14--23\% longer than they do now. By default,
Rust's release builds split a crate into 16 codegen units by heuristics
over the whole crate, and LLVM inlines within each separately, so when
we changed the hasher of Rust's hash tables, the standard library's
sort, which uses no hash table, compiled differently and took 7--16\%
longer; the Rust is now built as one unit, with link-time optimisation.

\paragraph{Searching an array.} The quadratic algorithms ask on every
draw whether a number is already in the output. A C++ loop that returns
at the first match is not vectorised, because of the early exit; one
that ORs every comparison together is. With libc++ we also tried
\mintinline{cpp}{std::ranges::contains}, which on long arrays scans
almost twice as fast as our loop, but for 4-byte integers is a call to
glibc's \mintinline{c}{wmemchr}, and the call costs more than a short
scan does. The quadratic algorithms are only worth having where the
scans are short, so we kept our loop. In ns per number, for C++
quadratic rejection in random order at \(n = 1{,}346{,}269\):

\begin{center}
    \small
    \begin{tabular}{r|r|r|r}
    \(k\) & Returning early & ORing together &
    \mintinline{cpp}{std::ranges::contains} \\
    \hline
    8 & 2.48 & 1.86 & 5.04 \\
    34 & 8.35 & 2.65 & 5.24 \\
    144 & 38.3 & 3.96 & 5.28 \\
    610 & 153 & 10.2 & 7.39 \\
    10,946 & 2,483 & 169 & 91.7
    \end{tabular}
\end{center}

\paragraph{Defaults.} On x86-64, both compilers target the original
baseline, whose only vectors are SSE2, unless told otherwise. Built
that way, the quadratic algorithms, whose scans then use vectors half
as wide, take 1.7 to 3.9 times as long from \(k = 610\) up; SELECT's
fill takes up to 1.2 times as long; and the C++ sorted bit-vector F2
takes 1.4 to 1.8 times as long at small \(k\), where its time goes on
scanning for set bits. We build both languages for the AVX2 baseline,
x86-64-v3. We also build without the hardening flags that Nix's
compiler wrapper adds and the libstdc++ assertions that Meson turns on,
as an ordinary optimised build would be, though neither changed any C++
time by more than 9\%; and we build the C++ with clang rather than
Nix's default of GCC, so that the two languages differ in their
libraries and not their compilers.

\paragraph{Libraries.} Which library provides a hash table or a sort
changes the results more than most of the effects here. The C++
standard library's hash tables are node-based, and Boost's flat tables
insert 4 to 16 times as fast; with them, the C++ Floyd's F2, HSEL and
set-based rejection take about 0.2 times as long in random order.
Rust's default hasher, SipHash, resists collision attacks that Boost's
does not, and foldhash inserts about 1.6 times as fast. Switching the
C++ standard library from libstdc++ to libc++ made Cardchoose take
about 0.55 times as long, because the two
\mintinline{cpp}{std::sort}s are different code. With each language's
standard library alone, a comparison of the two languages would largely
have compared their hash tables.

\paragraph{Memory from the kernel.} glibc's \mintinline{c}{malloc}
serves blocks over 32\,MB with a fresh \mintinline{c}{mmap} and unmaps
them when freed, so an algorithm that allocates a large array on every
call faults in every page of it again on every call: SELECT from \(n\)
of about 8 million, and the bit-vector F2 from about 270 million. The
results are timed with ordinary 4\,kB pages, which is what a program
gets unless it asks for something else, but we also timed 20 points
with glibc taking its memory in 2\,MB pages. The algorithms whose time
goes on cache misses in a large table get faster, since each miss no
longer also misses in the TLB: by 5\% for Rust RANKSB at
\(n = k = 3{,}524{,}578\), and 17\% for the C++ bit-vector F2 at
\(n = 165{,}580{,}141\). SELECT at \(n = 14{,}930{,}352\) takes 0.22
times as long, since 14,600 page faults a call become 29; but at
\(n = 1{,}346{,}269\) it takes twice as long, since glibc then maps
even a 5\,MB array afresh on every call. So the page size changes which
algorithm is fastest at some points, in both directions.

\paragraph{One process for many points.} An earlier harness timed all
of an algorithm's points in one process, and a point's time then
depended on the points before it. Rust quadratic rejection and sorted
quadratic F2, which search the output with
\mintinline{rust}{slice::contains}, sometimes took about 1.6 times as
long at a whole run of points, with the same code, data and draws, and
which points were slow changed from run to run. The counters show the
scan's loop taking 2.3 cycles per iteration rather than 1.5, and
retiring 3.0 operations per cycle rather than 4.5: of the eight slots
in which the core can dispatch operations each cycle, 4.8 rather than
2.1 are empty because the front end has none to offer. Every operation
still comes from the op cache, and there are no more cache misses, TLB
misses or branch mispredictions. We ruled out the host, the data,
where the output array starts, moving between cores, transparent huge
pages and the passage of time, and have not found the trigger; but
where the process's memory lies has a part in it, since of 20 fresh
processes that each timed one such point, one was in the slow state
with the address space randomised, and none with randomisation off.
With each point in a process of its own the slow state is rare, and
cannot outlast the point that met it.

\paragraph{The prefetcher.} Filling a 185\,kB array with consecutive
numbers, as SELECT begins by doing, runs at two speeds 1.3 times apart:
the same 16,209 instructions take 3,370 cycles or 4,255. Nothing we can
count differs in cache misses, TLB misses or branch mispredictions. What
differs is the level-2 cache's prefetcher, which makes one or two
requests during a fast fill and about 1,160 during a slow one, for
lines that cache already holds. This is a correlation: the virtual
machine gives us no way to turn the prefetcher off and see the slow
speed go away. Which speed a process gets depends on where its memory
lies, in a way we have not been able to predict; with 2\,MB pages it is
always the slow one. We time this fill alone alongside the algorithms,
so that the results show which speed it took. SELECT at
\(n = 46{,}368\) runs at the slow speed in both languages, in every
process, with the same 1,250 or so requests a call. This is a property
of the processor rather than of the measurement, and a program that
calls SELECT will meet it too; it makes SELECT's times the least
certain of those we report.

\paragraph{How well the runs agree.} Of the 52,561 points timed in all
three runs, the number at which one run took more than a given amount
longer than the fastest is:

\begin{center}
    \small
    \begin{tabular}{r|r|r}
    Longer by more than & The slowest run & The second fastest run \\
    \hline
    3\% & 7,702 & 1,999 \\
    5\% & 4,989 & 1,082 \\
    10\% & 2,152 & 379 \\
    20\% & 623 & 92 \\
    50\% & 53 & 3
    \end{tabular}
\end{center}

So all three runs are within 5\% of each other at nine points in ten,
and at 97.9\% of points the time we report was reached by a second run
to within 5\%, and at 99.3\% to within 10\%. In every large
disagreement we looked at, the runs executed the same instructions, and
one took more cycles over them. Of the 92 points whose two fastest runs
differ by more than 20\%, 51 are SELECT's and 17 the bit-vector F2's,
which also sweeps an array whose size goes with \(n\); these are the
prefetcher's doing, and more runs would not settle them. Rust sorted
SELECT at \(n = 196{,}418\), timed in 180 processes on one boot, took
more than 1.2 times its fastest time in 124 of them. Of the others, 23
have \(k \geq 500{,}000\), where the time goes on cache misses in a
large table: one of the three boots was up to 2.2 times slower than the
others at some such points, with the same level-2 cache misses, so the
time went beyond that cache, perhaps on a level-3 cache shared with
other tenants or on a slower host. Seven such points, each timed in 180
processes on one boot, did not drift over the hour, but the typical
process was 4\% to 13\% above the fastest. Lastly, at small points a
process is now and then 1.5 to 2 times slower at every stack position
while its neighbours are not; in 180 processes at each of six such
points this happened twice, seconds apart, and three runs clear nearly
all of these. We would not read anything into a difference of less than
5\% between two algorithms at a point, nor less than 10\% where \(k\)
is in the millions. The three runs are in \texttt{runs.tar.xz}, attached
to the
\href{https://github.com/ciphergoth/sansreplace/releases/tag/arxiv_01}{release}
of the repository that this paper describes, and \texttt{python/agree}
computes the table above from them.

\paragraph{How we checked.} Every change to an algorithm is checked for
fairness, by counting how often each possible output comes up at a few
small points. A time that changes unexpectedly is timed again on a
fresh boot before we believe it; to tell a real change from noise, the
old and new code are built and timed alternately, on one boot, at the
same points. When a time changes but the source has not, we compare the
machine code of both builds, on the machine the results are timed on,
so that ``the code is the same'' is something we have checked rather
than assumed; and where it is the same, we read the performance
counters to see where the time goes.
