\title{Cardchoose: simple, fast sampling without replacement}
\author{Paul~Crowley}
\affil{Anthropic PBC}

\begin{document}
\maketitle
\begin{abstract}
    We present Cardchoose, a new algorithm for choosing \(k\) distinct
    natural numbers below \(n\) such that every set of \(k\) is equally
    likely. It draws a multiset of \(k\)
    values below \(n - k + 1\) with a P\'olya urn, which makes every
    multiset equally likely, then sorts it and adds each value's index,
    which by the stars and bars bijection turns it into a set. It is a
    few lines of integer arithmetic and a call to a standard sort, needs
    no memory beyond the output array, and takes \(\bigO{k \log k}\)
    time. We benchmark C++ and Rust implementations of it and eleven
    other algorithms over a wide range of \(n\) and \(k\), for both
    sorted and random order output. No algorithm is close to the fastest
    everywhere, but scored by the worst time per number output in each
    decade of \(k\), Cardchoose is the best single algorithm in three of
    the four cases and the best that needs no floating point in all
    four, and it is never more than 9 to 22\,ns per number slower than
    the best set of three algorithms, choosing between them based on
    \(n\) and \(k\). Of the three algorithms whose time per number
    output is never far above the fastest's, it is the simplest; with a
    fast sort, as in Rust, it is the best algorithm for sorted output at
    every \(k\) below \(10^7\).
\end{abstract}

\section{Introduction}

Sampling without replacement means choosing \(k\) distinct numbers
from \(\{0, 1, \ldots, n-1\}\) such that every \(k\)-element subset is
equally likely to be returned. Many programming languages include facilities for this in
their standard libraries, for example Python's
\mintinline{python}{random.sample()} or Rust's
\mintinline{rust}{rand::seq::index::sample}; Ting \cite{ting} lists
the algorithms that several of them use.

We present Cardchoose, a new algorithm for this problem, which we
first proposed in October 2018. It chooses a multiset
with a P\'olya urn and turns it into a set with a sort, so that it is a
few lines of integer arithmetic and a call to a standard sort. It needs
no memory beyond the array in which the result is written, and takes
\(\bigO{k \log k}\) time. \autoref{cardchoose} explains it and proves
it fair, and \autoref{priorart} places it relative to earlier work.

Many other algorithms solve this problem, with different strengths.
Some are fast only for certain values of \(k, n\), for example where
\(k\) is small or where \(\frac{n}{k}\) is small. Some update a
hash-based data structure such as a set or dictionary for each value
generated, which adds memory and a significant constant factor to the
runtime. Some need extra memory proportional to \(n\), or
floating-point arithmetic. To see where Cardchoose stands among them,
in \autoref{otheralgs} we describe eleven of them alongside it, and in
\autoref{benchmarks} we compare C++ and Rust implementations of each.
No single algorithm is close to the fastest for all \(n, k\), so in
\autoref{choosing} we find the small sets of algorithms that between
them come closest, which are what a library might choose between, and
show that Cardchoose alone is never far behind them. Along the way, in
\autoref{quadraticf2}, we give a way to keep a quadratic version of
Floyd's F2 in random order that needs no extra random draws.

\subsection{Notation}

Let \(\NN_{<n} \defeq \{i \in \NN: i < n\}\), the set of natural
numbers less than \(n\) where \(\NN = \{0, 1, 2, \ldots\}\). Let
\(\binom{S}{k} \defeq \{s \subseteq S: |s| = k\}\), the set of all
\(k\)-element subsets of \(S\); note that \(\left|\binom{S}{k}\right|
= \binom{|S|}{k}\).

A \emph{multiset} is an extension of a set in which elements can
appear more than once; we use brackets to delimit the elements of a
multiset, so $[0, 1, 1]$ is the same multiset as $[1, 0, 1]$ but
distinct from $[0, 0, 1]$. Define \(\multichoose{U}{k}\) to be the set
of multisets of cardinality \(k\) whose elements are drawn from
\(U\), and \(\multichoose{n}{k} \defeq
\left|\multichoose{\NN_{<n}}{k}\right|\) the number of distinct
\(k\)-cardinality multisets over an \(n\)-element universe.

\subsection{Subsets as stars and bars}\label{starsandbars}

Write the numbers \(0, \ldots, n-1\) in a row, marking each chosen
number as a star and each unchosen one as a bar. For \(n = 7\), \(k =
3\) and the subset \(\{1, 2, 5\}\):

\begin{displaymath}
    \begin{array}{ c c c c c c c }
        0 & 1 & 2 & 3 & 4 & 5 & 6 \\
        \big| & \star & \star & \big| & \big| & \star & \big| \\
    \end{array}
\end{displaymath}

A row of \(k\) stars and \(n - k\) bars is exactly a \(k\)-element
subset of \(\NN_{<n}\): the stars' positions are the chosen numbers.
Following Feller \cite[Chapter II \S 5]{feller}, think of the spaces
between bars, including the space at each end, as \emph{cells}, and
number them from \(0\). Instead of its position, we describe each star
by its \emph{cell number}, the number of bars to its left:

\begin{displaymath}
    \begin{array}{ c c c c c c c }
        \big| & \star & \star & \big| & \big| & \star & \big| \\
          & 1 & 1 & & & 3 & \\
    \end{array}
\end{displaymath}

A cell number can be anything from \(0\) (before all the bars) to
\(n - k\) (after all of them), so there are \(t = n - k + 1\) cells,
and stars can share a cell. The cell numbers of the stars therefore
form a multiset in \(\multichoose{\NN_{<t}}{k}\). This is a bijection between
\(\binom{\NN_{<n}}{k}\) and \(\multichoose{\NN_{<t}}{k}\). Going one
way, read off each star's cell number. Going back, the multiset says
how many stars go in each cell, and that rebuilds the row. The two directions undo each other, so
each subset corresponds to exactly one multiset and each multiset to
exactly one subset; in particular \(\multichoose{t}{k} =
\binom{t + k - 1}{k}\).

In code, the way back is: sort the multiset, then add each star's
index to its cell number, because a star's position is its bars to the left
plus its stars to the left:

\begin{displaymath}
    \begin{array}{ l c c c }
        \text{sorted cell numbers} & 1 & 1 & 3 \\
        \text{+ index} & 0 & 1 & 2 \\
        \text{positions} & 1 & 2 & 5 \\
    \end{array}
\end{displaymath}

That is the last three lines of the algorithm. Because the
correspondence is a bijection, choosing a multiset uniformly at
random and converting it gives a subset chosen uniformly at random:
each subset is reached from exactly one multiset. So what remains is
to choose an element of \(\multichoose{\NN_{<t}}{k}\) fairly.

\subsection{Choosing a multiset fairly}\label{fairmultiset}

Putting each of \(k\) stars in a cell chosen independently from
\(\NN_{<t}\) does not give a uniform multiset. With \(t = 2\), \(k = 2\), the multiset \([0, 1]\)
comes up half the time, because it can arrive as \(0, 1\) or as \(1,
0\), while \([0, 0]\) and \([1, 1]\) get a quarter each. Independent
draws favour variety; we need to favour repeats, by exactly the right
amount.

Instead, build the row one star at a time, starting from the \(t -
1\) bars alone, and put each new star in a uniformly random slot of
the row so far: a place between two neighbouring symbols, or at either
end. With \(i\) stars already placed, the row holds \(t - 1 + i\)
things, so it has \(t + i\) slots. Name each slot by what is just to
its left:
\begin{itemize}
    \item The slot at the start of the row, and the slot just after
    each bar. There are \(t\) of these, and a star placed in the one after
    the \(b\)-th bar, or at the start for \(b = 0\), goes in cell \(b\).
    These are the \emph{fresh} slots.
    \item The slot just after each star. There are \(i\) of these, and
    a star placed in one goes in the same cell as its left neighbour.
    These are the \emph{copy} slots.
\end{itemize}
For example, with \(t = 4\), so three bars, and two stars already
placed, \(d = [1, 3]\), there are six slots, each marked \(\circ\) here
with the \(r\) that picks it above and the cell it gives below:

\begin{displaymath}
    \begin{array}{ l c c c c c c c c c c c }
        r & 0 & & 1 & & 4 & & 2 & & 3 & & 5 \\
        \text{row} & \circ & \big| & \circ & \star_0 & \circ & \big| & \circ & \big| & \circ & \star_1 & \circ \\
        \text{cell} & 0 & & 1 & & 1 & & 2 & & 3 & & 3 \\
    \end{array}
\end{displaymath}

That is the loop. \mintinline{python}{randrange(t + i)} picks a slot.
If \(r < t\), it is a fresh slot, and the new star goes in cell \(r\).
Otherwise \(r - t\) picks one of the stars already placed, and the new
star goes in its cell, \mintinline{python}{d[r - t]}. The list
\mintinline{python}{d} holds cell numbers in the order they were
drawn, so
the copy is a single index lookup: one random number, one comparison
and one write per star, with no search.

A cell that already holds \(c\) stars owns \(c + 1\) slots: one fresh
slot, and one after each of those stars. So a cell holding one star is
now twice as likely to get the next one as an empty cell, a cell
holding two three times as likely, and so on. The slots are the balls
of a P\'olya urn (\autoref{priorart}): the \(t\) fresh slots are \(t\)
balls, one of each colour, and each star adds a copy slot to its cell,
as each draw adds a ball of the colour drawn. That is how repeats get
favoured; the next subsection shows it is by exactly the right amount.

\subsection{Proof}\label{proof}

Tag each star with the number of the draw that placed it. Different
values of \(r\) put the new star in different slots, so a tagged row
records its whole history: remove the highest-tagged star, and its
left neighbour says which slot it went in, so whether it was fresh (a
bar, or nothing) or a copy (a star, and which one). Repeat to recover
every draw. So distinct sequences of draws produce distinct tagged
rows.

\autoref{sixruns} lists every possible run for \(t = 2\), \(k = 2\),
one bar and two stars. Every run has the same probability, \(\frac{1}{2}
\times \frac{1}{3}\), and the six results are the six tagged rows:
three ways to place two stars around a bar, times two ways to tag
them.

\begin{table}
    \begin{tabular}{ l l l l }
        first draw & row & second draw & row \\
        \hline
        \(r = 0\), fresh, cell 0 & \(\star_1 \,\big|\) & \(r = 0\), fresh, cell 0 & \(\star_2 \star_1 \,\big|\) \\
        & & \(r = 1\), fresh, cell 1 & \(\star_1 \,\big|\, \star_2\) \\
        & & \(r = 2\), copy \(\star_1\) & \(\star_1 \star_2 \,\big|\) \\
        \(r = 1\), fresh, cell 1 & \(\big|\, \star_1\) & \(r = 0\), fresh, cell 0 & \(\star_2 \,\big|\, \star_1\) \\
        & & \(r = 1\), fresh, cell 1 & \(\big|\, \star_2 \star_1\) \\
        & & \(r = 2\), copy \(\star_1\) & \(\big|\, \star_1 \star_2\) \\
    \end{tabular}
    \caption{Every run for \(t = 2\), \(k = 2\)}\label{sixruns}
\end{table}

In general there are \(t (t + 1) \cdots (t + k - 1) = \frac{(t + k -
1)!}{(t - 1)!}\) sequences of draws, each with probability
\(\frac{(t - 1)!}{(t + k - 1)!}\), and the same number of tagged
rows: \(\binom{t + k - 1}{k}\) ways to place the stars among the
bars, times \(k!\) ways to tag them. Since distinct sequences give
distinct tagged rows, every tagged row is produced by exactly one
sequence, and so every tagged row is equally likely. Each untagged
row has exactly \(k!\) taggings, so every untagged row is equally
likely, which is to say every multiset in
\(\multichoose{\NN_{<t}}{k}\), which is to say, by
\autoref{starsandbars}, every subset in \(\binom{\NN_{<n}}{k}\). In
\autoref{sixruns}, each of the three untagged rows is the result of
two runs, so each has probability \(\frac{1}{3}\).

\subsection{Prior art}\label{priorart}

This subsection mentions several of the other algorithms, which
\autoref{otheralgs} describes.

Physicists have names for the three distributions in this story
\cite[Chapter II \S 5]{feller}. Distinguishable particles placed independently in
cells, the biased way of picking a multiset in \autoref{fairmultiset},
is Maxwell--Boltzmann statistics. Indistinguishable particles with every
occupancy pattern equally likely, a uniform multiset, is Bose--Einstein.
At most one particle per cell with every pattern equally likely, a
uniform subset, is Fermi--Dirac. Stars and bars is the standard way to
count the Bose--Einstein configurations, by matching them with
Fermi--Dirac ones. So the one-line summary of Cardchoose is: generate
a Bose--Einstein configuration with a Pólya urn, then map it to
Fermi--Dirac by stars and bars.

The mathematics of both halves is classical. The multiset loop is a
Pólya urn \cite[Chapter V \S 2]{feller}: start with \(t\) balls, one of each
colour; draw a ball uniformly at random, and put it back along with a
new ball of the same colour. The urn is a textbook object of study, and
that with one ball of each colour its counts are uniform, which is to
say Bose--Einstein, is a standard lemma about it
\cite[Lemma 2.7]{levinperes}; Niven and Grendar \cite{nivengrendar} map
all three statistics onto the urn, with Maxwell--Boltzmann as
replacement without a copy, Bose--Einstein as replacement with a copy,
and Fermi--Dirac as no replacement. But the urn is presented as a model,
not as a way to generate anything, beyond passing remarks that it could
be used so \cite{cancriniposta}. The nearest thing to running an urn as
a sampler in earnest is in Bayesian statistics, where the
Blackwell--MacQueen urn \cite{blackwellmacqueen} draws an exchangeable
sequence from a Dirichlet process, which is a different purpose. The
combinatorial generation literature does generate random multisets, but
through stars and bars in the other direction: Nijenhuis and Wilf's
RANCOM \cite[Chapter 6]{nijenhuiswilf} chooses a random
\((k-1)\)-subset of \(\{1, \ldots, n+k-1\}\) and differences it.
Nor do surveys of sampling without replacement describe anything like
it: Devroye's \cite[Chapter XII]{devroye} has no urn and no stars and
bars, and Ting \cite{ting}, reworking the classical algorithms into
simpler forms, gives a sparse Fisher--Yates sampler, essentially HSEL,
and a sorted sampler that draws each skip from a beta-binomial
distribution, which needs floating point. What is new in Cardchoose
is the urn used as a generator for uniform multisets, and its
composition with stars and bars into a sampler for sampling without
replacement. Needing no set, map or extra
memory is not new in itself: Nijenhuis and Wilf's RANKSB
\cite[Chapter 4]{nijenhuiswilf} also uses nothing but the output
array, and so do Vitter's Algorithm D and, more recently, Shekelyan and
Cormode's Hidden Shuffle \cite{hiddenshuffle}, though they need
floating-point arithmetic where Cardchoose and RANKSB use only exact
integer draws.

The earlier algorithm closest to Cardchoose is Gupta and
Bhattacharjee's GSEL \cite{gupta}, which also takes
\(\bigO{k \log k}\) time and can return sorted output. Like SELECT, it
draws its \(i\)th value uniformly from the \(n - i + 1\) values not yet
chosen, as a rank \(r\) among them; that value is \(r + u\), where \(u\)
is the number of values already chosen below it, and GSEL finds \(u\)
in a balanced binary tree of the chosen values that records the size
of each subtree, as Ernvall and Nevalainen \cite{hsel} had suggested
in passing to bound HSEL's worst case. Rouzankin and Voytishek \cite{RouzankinVoytishek} do
the same with a sorted array, in \(\bigO{k^2}\) time, and with an
unbalanced binary search tree, in \(\bigO{k \log k}\) expected time;
they also split the range in half recursively, drawing how many values
fall in each half from a hypergeometric distribution, which with
stored tables of its probabilities takes \(\bigO{k}\) expected time,
and is the division Sanders et al.\ \cite{sandersetal} use to sample
in parallel. Adding to each value the number of chosen values
below it is also the last step of Cardchoose, where each sorted value
has its index added. But GSEL must keep its chosen values in order to
count as it goes, and so needs a tree of \(k\) nodes, while the urn
never needs the earlier values in order, so Cardchoose can leave the
counting to a single sort at the end, in the output array. We have
not benchmarked GSEL: besides needing memory that Cardchoose does not,
it follows pointers through the tree for every value drawn, where
Cardchoose makes one sort over a flat array, and we see no way for it
to be faster.

Sorted output without a sort has a classic answer for real numbers:
Bentley and Saxe \cite{bentleysaxe} generate \(k\) sorted uniform
reals in \(\bigO{k}\) time, drawing the largest as \(U^{1/k}\) and
repeating for the rest below it, and credit Friedman \cite{friedman}
with an essentially equivalent earlier program. This cannot stand in
for the urn: sorted independent draws, even rounded to integers, follow
the Maxwell--Boltzmann distribution over multisets, not the
Bose--Einstein one. Its closest analogue for distinct integers is
Vitter's Algorithm D, whose continuous approximation is the same step.

\section{Benchmarked algorithms}\label{otheralgs}
We compare Cardchoose with eleven other algorithms. Though the literature includes algorithms that return an
iterator, we here focus on algorithms that return an array of \(k\)
elements. Some applications require that the returned elements be in
sorted order, while others need the order of the elements to be a fair
random draw. Both Python's \mintinline{python}{random.sample()} and
Rust's \mintinline{rust}{rand::seq::index::sample} return in a fair
random order.

An algorithm that returns one order can be made to return the other
with a sort or a Fisher--Yates shuffle. But each algorithm returns one
order naturally, and the other costs that extra step, so which
algorithm is fastest can depend on which order the caller wants. In
our benchmarks we time both a sorted and a random variant of every
algorithm.

For each algorithm we give how it works, the order it returns, its
expected time, and any memory it needs beyond the output array, and a
Python listing for all but RANKSB, Algorithm D and Hidden Shuffle,
whose code is too long to list, and Cardchoose, whose listing is in
\autoref{cardchoose}; the repository has Python
implementations of all twelve, in
\href{https://github.com/ciphergoth/sansreplace/tree/master/python/algorithms}{\texttt{python/algorithms}}. All but two draw only random integers below a bound;
Vitter's Algorithm D and Hidden Shuffle also need floating-point
arithmetic.

\begin{center}
    \begin{tabular}{l|l|l|l|l}
    Algorithm & Time & Order & Extra memory & Floats \\
    \hline
    Quadratic rejection sampling & \(k^2\) & Random &  & \\
    Set-based rejection sampling & \(k\) & Random & Set & \\
    Floyd's F2 & \(k\) & None & Set & \\

reject draws slow down as \(k\) approaches \(n\).

\subsection{Quadratic rejection sampling}
\inputminted{Python}{code/quadraticreject.py}
Draw a value below \(n\), check whether it is already in the output by
scanning the output so far, and append it if not; repeat until the
output has \(k\) values. The output is in random order and no extra
memory is needed. Each check takes \(\bigO{k}\) time, so the whole
takes \(\bigO{k^2}\) expected time for \(k \leq n/2\), and more as
\(k\) approaches \(n\) and more draws are rejected, as for set-based
rejection sampling below.

\subsection{Set-based rejection sampling}
\inputminted{Python}{code/rejectionsample.py}
As above, but check each draw against a set of the values chosen so
far, with an efficient membership test \cite{goodman}. Teuhola and
Nevalainen \cite{teuhola} and Ahrens and Dieter \cite{ahrensd} keep
the set in a hash table, and Devroye \cite[Chapter XII \S 2]{devroye}
compares the data structures that can hold it. The output is in random
order, and the set takes \(\bigO{k}\) memory. With a hash table, this
takes \(\bigO{k}\) expected time for \(k \leq n/2\), where each draw is
rejected with probability at most a half; Jakobsson \cite{jakobsson}
shows that the expected number of draws is then less than
\(2k \ln 2 \approx 1.39k\). As \(k\) approaches \(n\), rejections
mount: the expected number of draws is \(n(H_n - H_{n-k})\), where
\(H_m\) is the \(m\)th harmonic number, so at \(k = n\) it takes
\(\bigO{n \log n}\) time.

\subsection{Floyd's F2}
\inputminted{Python}{code/floydf2.py}
Build a set of the values chosen so far, one value per step, with no
rejection \cite{floydf2}. Before the step for \(m\), running from
\(n - k\) to \(n - 1\), the set is a uniformly random subset of
\(\NN_{<m}\). Draw \(j\) uniformly from \(\NN_{<m + 1}\), and add
\(j\) if it is not in the set, or \(m\) if it is; \(m\) is never in the
set before its own step, so the set grows by one, and it is then a
uniformly random subset of \(\NN_{<m + 1}\). This makes exactly \(k\)
draws and takes \(\bigO{k}\) expected time with a hash set, which
takes \(\bigO{k}\) memory, and the result has no order. For random
order output, our C++ and Rust implementations do not shuffle
afterwards. Instead, as in Ting's random-order version of Floyd's
algorithm \cite{tingblog}, when the chosen value is already present,
they move a randomly chosen earlier output to the end and put the new
value in its place. This keeps the order uniformly random, and costs an
extra random number only on collisions.

\subsection{Quadratic F2}\label{quadraticf2}
\inputminted{Python}{code/quadraticf2.py}
Floyd's F2 with the output array as its set, scanned to check each
draw, so that it needs no extra memory and takes \(\bigO{k^2}\) time.
When the draw \(r\) is already present, it replaces that entry with
\(m\) and appends \(r\), which keeps the output in uniformly random
order without a shuffle or any extra draw: the scan has already found
where \(r\) is, which Floyd's F2 with a set does not know. Rust's \mintinline{rust}{rand} crate used
Floyd's F2 with a scan in the same way \cite{rust-random}, but kept
the order random either by inserting \(m\) before the matching entry,
which shifts every entry after it, or by shuffling the whole output
afterwards, which costs \(k\) more draws. It has used our version
since 2023; the pull request that made that change \cite{randpr} is
the first publication of this way of keeping the order random that we
know of. For sorted output,
our implementations append \(m\) instead, since before the sort only
the set matters, and then sort.

\subsection{Iterative choosing (Algorithm S)}
\inputminted{Python}{code/iterativechoose.py}
Go through the values of \(\NN_{<n}\) in order, and choose each with
the probability that it is in the sample given how many values are
still to choose and how many remain to consider
\cite[Method 1, p.391]{fanetal}; this is Knuth's Algorithm S
\cite{taocp2}. The output is sorted, no extra memory is needed, and it
makes one draw for every value it considers, so it takes \(\bigO{n}\)
time.

\subsection{Reservoir sampling (Algorithm R)}
\inputminted{Python}{code/reservoirsample.py}
Fill the output with the elements of \(\NN_{<k}\) in random order.
Then for each \(i\) from \(k\) to \(n - 1\), draw \(r\) from
\(\NN_{<i + 1}\), and if \(r < k\), replace the \(r\)th output with
\(i\); this is Knuth's Algorithm R \cite{taocp2}. The output is in
random order, no extra memory is needed, and it makes one draw for
every value, so it takes \(\bigO{n}\) time. Vitter's Algorithm Z
\cite{vitterZ} instead draws how many elements to skip, which takes
\(\bigO{k(1 + \log(n/k))}\) expected time but, like Algorithm D below,
needs floating point; we time only Algorithm R.

\subsection{RANKSB}
Divide \(\NN_{<n}\) into \(k\) bins of nearly equal size. First
decide how many of the chosen values fall in each bin, by simulating
set-based rejection sampling while keeping only a count for each bin:
a draw is rejected with the probability that it would duplicate a value
already accepted in its bin, which depends only on that bin's count.
Then choose that many values within each bin; bins hold about one value
each, so a quadratic method suffices. The output is sorted, the expected
time is \(\bigO{k}\) for \(k \leq n/2\), and the program in
\cite[Chapter 4]{nijenhuiswilf} needs no memory beyond the output
array. Our C++ and Rust implementations follow that program, except
that they fill each bin as soon as they know where its values go,
rather than first marking out every bin's slots and then scanning for
the marks.

\subsection{Vitter's Algorithm D}
Like iterative choosing, produce the output in sorted order, but
instead of deciding about each value in turn, draw the number of values
to skip before the next chosen one directly. The skip has a known
discrete distribution, which Algorithm D samples by rejection from a
continuous approximation, the smallest of \(k\) uniform reals drawn in
one step as in \cite{bentleysaxe}, in \(\bigO{1}\) expected time per
output, at the cost of a few floating-point exponentiations, and with
no extra memory. Once \(n \leq 13k\) it falls back on Vitter's
Algorithm A, which draws each skip in time proportional to its length.
Vitter introduced Algorithm D in \cite{vitterfaster}; our
implementation follows the improved code in the appendix of
\cite{vitterD}, which is too long to list here. Ahrens and Dieter
\cite{ahrensd} give other sequential methods that take \(\bigO{k}\)
time, and Ting \cite{ting} one that draws each skip from a
beta-binomial distribution; like Algorithm D, these draw their skips in
floating point, and we take Algorithm D and Hidden Shuffle to represent
them.

\subsection{Hidden Shuffle}
Shekelyan and Cormode's Hidden Shuffle \cite{hiddenshuffle} considers
a Fisher--Yates shuffle of \(\NN_{<n}\) that stops after \(k\) steps,
so that the sample is whatever ends up in the first \(k\) positions;
call these the low positions, and the rest the high positions. Each
step reaches a high position independently, with known probability,
and which high position it reaches is uniform and independent of
everything else. So first count the steps that reach a high position,
then draw that many high positions with replacement in sorted order as
in \cite{bentleysaxe}. The first draw of a high position adds its value
to the sample; a repeat finds a low value swapped there earlier, so the
sample gains a low value instead, much as a collision in Floyd's F2
adds a different value. Given their number, the low values are a
uniformly random subset of the low positions, chosen in order by
Vitter's Algorithm A. The output is sorted, the time is \(\bigO{k}\) in
the worst case, and no extra memory is needed; like Algorithm D, it
relies on floating-point arithmetic, with an exponentiation for each
high draw. The code printed in the paper can divide by zero, and its
last step has an off-by-one error that biases the output; our
implementations apply the corrections from the errata in
\cite{sampleiterator}. We thank metasj for bringing this algorithm to
our attention.

\subsection{SELECT}
\inputminted{Python}{code/select.py}
Fill an array with the elements of \(\NN_{<n}\), and run the first
\(k\) steps of a Fisher--Yates shuffle on it: at step \(i\), swap a
random element from position \(i\) onwards into position \(i\)
\cite{goodman}. The first \(k\) elements are then the sample, in
random order. It makes only \(k\) draws, but the array takes
\(\bigO{n}\) memory and \(\bigO{n}\) time to fill.

\subsection{HSEL}
\inputminted{Python}{code/hsel.py}
SELECT with a ``virtual'' array: a hash table stores only the elements
that have changed, so it needs no \(n\)-element array
\cite{hsel}. The output is in random order, and it takes \(\bigO{k}\)
expected time and \(\bigO{k}\) memory for the hash table. Teuhola and
Nevalainen \cite{teuhola} give a version that needs \(2k\) storage
locations rather than about \(5k\), which draws all \(k\) random
numbers first and then works out which value each one stands for,
from the last back. Our C++ and Rust implementations use a faster
variant, which keeps the first \(k\) entries of the virtual array in
the output array itself, so only swaps that reach beyond them touch
the hash table. This variant was described by rici \cite{rici}; we
thank Mathias Weller for bringing it to our attention.

\subsection{Cardchoose}
Described in \autoref{cardchoose}: choose a multiset of \(k\) cell
numbers below \(n - k + 1\) with a P\'olya urn, then sort it and add
each one's index to turn it into a set. The output is sorted, and the
only memory needed is the output array.

\section{Benchmarks}\label{benchmarks}

The accompanying repository
(\url{https://github.com/ciphergoth/sansreplace}) includes C++ and Rust
implementations of these algorithms, which were benchmarked for a
variety of values of \(n\) and \(k\), for both sorted output and
random output, on an AWS r8a.xlarge, whose four vCPUs are each a whole
physical core, so nothing shares the core a benchmark runs on:

\begin{itemize}
    \item CPU: AMD EPYC 9R45, four cores
    \item Cache: 48kiB L1 data and 1MiB L2 per core, 16MiB L3 shared
    \item Memory: 32GiB
    \item OS: NixOS 25.11, Linux 6.12
    \item C++ compiler: clang 21.1 with libc++, \verb|-O3 -march=x86-64-v3|
    \item Rust compiler: rustc 1.98, release profile, \verb|-C target-cpu=x86-64-v3|
\end{itemize}

We tested values of \(n\) and \(k\) that are Fibonacci numbers, with
\(n\) up to 701,408,733 (the 44th Fibonacci number) and \(k\) up to
102,334,155 (the 40th).

\subsection{Method}

A Python harness times each algorithm in a process of its own, calling
the C++ and Rust implementations through a C interface. At each point,
it times passes of more and more calls, until a pass takes up what is
left of 0.2 seconds, and records the mean time per call over that last
pass; a point where one call takes longer than that is timed with a
single call. The loop over calls runs in C++ or Rust, and every call
writes to the same output array, allocated outside the timing, aligned
to a 64-byte cache line and zeroed. The overhead of a call, measured by
timing a function that does nothing, is about 1.1\,ns, and is not
subtracted. Every process seeds its random number generator with the
same fixed value, and the C++ and Rust generators start in the same
state, so running the same code again makes the same draws. Timing the
same points on four separate boots of the machine, which may come back
on a different host each time, every algorithm agreed to within about
1\%. We describe what we found and changed to make these timings
trustworthy, such as aligning arrays that were otherwise slower to fill
depending on where earlier allocations left them, in
\href{https://github.com/ciphergoth/sansreplace/blob/master/measurement.md}{\texttt{measurement.md}} in the
repository.

\subsection{The two languages}

The C++ and Rust implementations are the same algorithms, written the
same way, and apart from random number generation each uses only its
own language's standard library, so the results show the performance
available from standard components. Some of those components differ a
great deal.

\paragraph{Hash tables.} The C++ uses libc++'s
\mintinline{cpp}{std::unordered_set} and
\mintinline{cpp}{std::unordered_map}, which are node-based: each entry
is allocated separately and reached through a linked list. Rust's
\mintinline{rust}{HashSet} and \mintinline{rust}{HashMap} are flat
open-addressing tables based on SwissTable. The hash-based algorithms
take about 0.3 times as long in Rust as in C++.

\paragraph{Sorting.} libc++'s \mintinline{cpp}{std::sort} is an
introsort, and Rust's \mintinline{rust}{sort_unstable} is ipnsort.
Sorting the same arrays of random numbers, \mintinline{cpp}{std::sort}
takes 1.15 to 1.84 times as long (\autoref{sorttimes}), and Cardchoose
takes about 0.5 times as long in Rust as in C++. RANKSB, Algorithm D
and Hidden Shuffle need neither a hash table nor a sort, and take about
the same time in both languages for sorted output.

\paragraph{Random numbers.} Both use the Xoshiro256++ generator, and
both turn its output into a number below a bound with a
multiplication. But the C++ uses its own code for this, which takes two
32-bit numbers from each 64-bit output, while the
\mintinline{rust}{rand} crate's \mintinline{rust}{random_range} uses a
whole output for each. The shuffle that turns the sorted output of
RANKSB, Algorithm D and Hidden Shuffle into random order is the same
loop in both languages, but adds 1.1 to 1.5 times as much time per
number in Rust, at the median in each decade of \(k\); so for random
output, Algorithm D and Hidden Shuffle take 4--8\% longer in Rust at
the median. The \mintinline{rust}{rand} crate's own
\mintinline{rust}{SliceRandom::shuffle} is slower than our loop.

\paragraph{Searching an array.} The quadratic algorithms search the
output so far on every draw. The Rust uses
\mintinline{rust}{slice::contains}, and the C++ a loop of its own that
the compiler vectorises, since libc++'s
\mintinline{cpp}{std::ranges::contains} calls \mintinline{c}{wmemchr},
which is slower for the short arrays where these algorithms are worth
using.

No algorithm is the fastest for all \(n, k\). Quadratic rejection

factors.

\autoref{choosing} compares the algorithms by their worst time per
number output in each decade of \(k\). The rest of this section
describes regions of \(n\) and \(k\), by the range of one algorithm's
time over another's.

For sorted output in C++, Hidden Shuffle is the fastest algorithm
wherever \(n \geq 16k\) and \(k \geq 1000\); there, Cardchoose takes
up to 2.4 times as long. In Rust, Cardchoose and Hidden Shuffle divide
the range by \(k\): wherever \(k < 1000\) and \(n \geq 2k\),
Cardchoose is the fastest algorithm or within 24\% of it, and Hidden
Shuffle takes up to 3.7 times as long, while for larger \(k\) they
trade places: wherever \(k \geq 10^5\) and \(n \geq 16k\), each is
within 27\% of the fastest, and Hidden Shuffle is the fastest wherever
\(k \geq 10^7\) and \(n \geq 16k\). Hidden Shuffle takes about the
same time in both languages, so the difference is in Cardchoose, most
likely in its sort. Hidden Shuffle is also faster than RANKSB wherever
\(n \geq 16k\) and \(k \geq 1000\) in both languages, with RANKSB
taking 1.1 to 2.7 times as long. As \(k\) approaches \(n\), RANKSB
slows down, taking up to 530 times as long as the fastest algorithm at
\(k = n\) in C++, and 870 times in Rust; \cite{nijenhuiswilf} pairs
it with iterative choosing (which Nijenhuis and Wilf refer to as RKS2)
for \(k \geq n/2\). Vitter's Algorithm D, with its fallback to
Algorithm A, has the smallest worst case of any single algorithm for
sorted output in Rust, and in C++ only Hidden Shuffle's is smaller.
Where \(n \geq 4k\), it takes 0.59 to 2.5 times as long as Cardchoose
in C++ and 0.92 to 5.0 times as long in Rust; where \(n < 2k\) and
\(k \geq 10^5\), it is faster than Cardchoose in both.

For random output, the hash-based algorithms are competitive only with
a fast hash table. With C++ standard library hash tables, Cardchoose is
faster than set-based rejection sampling, Floyd's F2 and HSEL at every
point with \(k \leq n/2\), where they take 1.10 to 8.9 times as long,
though Hidden Shuffle followed by a shuffle is faster still wherever
\(n \geq 16k\) and \(k \geq 1000\). With Rust's flat hash tables, HSEL
is faster than Cardchoose wherever \(1000 \leq k < 10^5\) and
\(n \geq 2k\), and Cardchoose is faster wherever \(k \geq 10^7\) and
\(n \geq 2k\); it is never more than 1.38 times slower than the fastest
of these four for \(k \leq n/2\). In both languages, SELECT is the
fastest algorithm wherever \(2k \leq n < 16k\) and \(n\) is under 8
million; for larger \(n\), its array is large enough that glibc's
\mintinline{c}{malloc} maps it afresh on every call, and faulting its
pages in again makes it up to 2.1 times slower than the fastest. The hash-based
algorithms slow down at large \(k\), once the hash table no longer fits
in cache, and as \(k\) approaches \(n\). In theory, their
\(\bigO{k}\) time should eventually beat Cardchoose's
\(\bigO{k \log k}\), but not at any \(k\) we tested: in Rust, wherever
\(k \geq 10^7\) and \(n \geq 2k\), Cardchoose takes 0.23 to 0.39 times
as long as each of them. For very large \(k\), a parallel
algorithm \cite{rajan, sandersetal} should generally be used; that of
Sanders et al.\ calls a sequential algorithm at the leaves of the
parallel tree it builds.

\section{Choosing algorithms}\label{choosing}

We score each algorithm by its worst time per number output in each
decade of \(k\): for each band, the most its time per call divided by
\(k\) reaches at any point with \(k\) in the band, over every \(n\)
tested. This says what it costs at worst, per number, for any \(n\)
and any \(k\) in that range. The bands start at \(k = 10\), 100,
1,000 and so on, the last running from \(10^7\) to the largest \(k\)
tested; below 10, per-call overhead swamps everything. Each band also
has a floor: the score of choosing the fastest of all twelve
algorithms separately at every point, which no algorithm or set of
algorithms can beat. We give worst cases rather than averages, since
any average depends on which values of \(n\) and \(k\) we chose to
test, and score each band of \(k\) separately since otherwise the
largest \(k\), where everything is slowest per number, would decide
every ranking.

\autoref{bandscpprandom} to \autoref{bandsrustsorted} give, for each
band, the best algorithm, with any within 3\% of it, which is within
the noise between runs, marked \(\approx\); where any of those needs floating point
(Hidden Shuffle and Algorithm D), the best algorithm that does not;
then Cardchoose, and the floor. Each algorithm was timed only until a
call took more than 30 seconds; only the quadratic algorithms reached
that, from \(k = 1.3 \times 10^6\).

Three algorithms are never far from the fastest per number output at
any \(k\): Cardchoose, Hidden Shuffle and Algorithm D are never worse
than 44\,ns per number in any case, while every other algorithm is
worse than 100\,ns per number somewhere it was tested. Cardchoose is
the simplest of the three: it is a few lines of integer arithmetic,
while the other two need floating point and are considerably more
involved. Algorithm D switches to Algorithm A once \(n \leq 13k\),
and Hidden Shuffle runs three stages in turn, the last of them
Algorithm A.

With sorted output, Cardchoose is the best algorithm at every \(k\)
below \(10^7\) in Rust, and Hidden Shuffle above that; in C++,
Cardchoose is the best below \(10^4\), tied with Hidden Shuffle from
\(10^4\), and Hidden Shuffle is the best from \(10^5\). With random output,
quadratic F2 is the best for small \(k\), below 1,000 in C++ and 100
in Rust, where it needs neither a sort nor a shuffle; in Rust, with its
fast hash tables, HSEL is the best from there to \(10^6\). Wherever
the best algorithm needs floating point, the best one that does not is
Cardchoose.

An algorithm is dominated by bands if another scores no worse in any
band and better in at least one. Eight algorithms are dominated by
bands in every case: Cardchoose dominates seven of them in every case,
quadratic rejection, set-based rejection, RANKSB, Floyd's F2, iterative
choosing, reservoir sampling and SELECT, and Hidden Shuffle dominates
the eighth, Algorithm D. Because a band's score is
the worst over every \(n\), that does not make them useless: iterative
choosing, reservoir sampling and SELECT are among the fastest where
\(n/k\) is small, and iterative choosing belongs to the best sets for
sorted output below. No algorithm is at least as fast as another at
every point timed in every case, but in each case Cardchoose is at
least as fast as some of the others at every point: in Rust with
sorted output, as fast as six of the other eleven.

Since no algorithm is the best at every \(k\), an implementation might
implement several, and choose which one to use based on the values of
\(n\) and \(k\). \autoref{cover} shows, for each language and
order, the best set of one, two or three algorithms, if each point uses
the fastest algorithm in the set. A set's score in a band is its worst
time per number output there, as for a single algorithm, and the table
gives the most that exceeds the band's floor, as a ratio, in the set's
worst band: \(1.00\times\) means the set is as good as all twelve
algorithms together in every band. It also gives the most each set is
slower than the best set of three, in time per number, in any band.
Where the best set needs floating point, it also gives the best set
that does not, or says that a third such algorithm is no better than
two. This assumes the best choice is made at every point; an
implementation has to choose by a rule, such as thresholds on \(k\)
and \(n/k\).

If an implementation has only one algorithm, Cardchoose is a good
choice. It is the best single algorithm in three of the four cases; in
the fourth, C++ with sorted output, only the two floating-point
algorithms beat it, because libc++'s \mintinline{cpp}{std::sort} is
slower than Rust's sort. It is the best integer-only algorithm in every
case. Implemented alone, it is never more than 9 to 22\,ns per number
slower than the best three algorithms together, in any case and at any
\(k\). Its largest ratios to the floor are where calls are cheap: with
random output, it is 3.53 times the floor in C++ and 2.58 times in Rust
for \(k < 100\), where quadratic F2 needs neither a sort nor a
shuffle, but no call to Cardchoose there takes more than 1.5\,\textmu
s. With sorted output, it is 2.29 times the floor in C++ and 1.56 times
in Rust for \(k \geq 10^7\), where Hidden Shuffle wins.
