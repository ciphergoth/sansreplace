\begin{abstract}
    A variety of algorithms exist for fairly choosing $k$ distinct
    natural numbers below \(n\). We describe twelve of them, among them
    one, cardchoose, which we believe to be new, and benchmark C++ and
    Rust implementations of each over a wide range of \(n\) and \(k\),
    for both sorted and random order output. No algorithm is close to
    the fastest everywhere: in each case the best single algorithm is
    somewhere 2.9 to 13 times slower than the fastest, while the best
    set of three, choosing between them based on \(n\) and \(k\), is
    never more than 1.3 to 1.8 times slower. Cardchoose needs no storage
    beyond the output array and takes $\bigO{k \log k}$ time, using an
    integer sort; it combines a P\'olya urn, which chooses a
    multiset fairly, with the stars and bars bijection between
    multisets and sets. It is the simplest of the three algorithms
    whose time per number output is never far above the fastest's, it
    belongs to the best set of two or three in three of the four cases,
    and with a fast sort it is the fastest algorithm for sorted output
    more often than any other.
\end{abstract}

\section{Introduction}

We consider the problem of choosing a subset of $\{0, 1, \ldots,
n-1\}$ such that every \(k\)-element subset is equally likely to be
returned. Many programming languages include facilities for this in
their standard libraries, for example Python's
\mintinline{python}{random.sample()} or Rust's
\mintinline{rust}{rand::seq::index::sample}.

Many algorithms solve this problem, with different strengths. Some are
fast only for certain values of \(k, n\), for example where \(k\) is
small or where \(\frac{n}{k}\) is small. Some update a hash-based data
structure such as a set or dictionary for each value generated, which
adds memory and a significant constant factor to the runtime. Some need
extra memory proportional to \(n\), or floating-point arithmetic. In
\autoref{otheralgs} we describe twelve algorithms, and in
\autoref{benchmarks} we compare C++ and Rust implementations of each.
Since no single algorithm is close to the fastest for all \(n, k\), we
also find the small sets of algorithms that between them come closest,
which are what a library should choose between.

One of the algorithms, which we call cardchoose, we believe to be new.
It needs no storage beyond the array in which the result is written,
and takes \(\bigO{k \log k}\) time. We first proposed it in October
2018; \autoref{starsandbars} to \autoref{proof} explain it,
and \autoref{priorart} places it relative to earlier work.

\section{Algorithms}\label{otheralgs}
Let \(\NN_{<n}\) denote the \(n\)-element set \(\{0, 1, \ldots,
n-1\}\). Though the literature includes algorithms that return an
iterator, we here focus on algorithms that return an array of \(k\)
elements. Some applications require that the returned elements be in
sorted order, while others need the order of the elements to be a fair
random draw. Both Python's \mintinline{python}{random.sample()} and
Rust's \mintinline{rust}{rand::seq::index::sample} return in a fair
random order.

A routine which returns one of these can straightforwardly be
converted into a routine that returns another, using a sort or a
Fisher-Yates shuffle as appropriate. However each of these algorithms
returns one of the above types ``naturally'', and so returning a
different one will take an extra step, which means that which
algorithm is most efficient can depend on which of the above three the
caller wants to receive. In our benchmarks, we time both a ``random''
and a ``sorted'' variant of each algorithm.

\subsection{Quadratic rejection sampling}
\inputminted{Python}{code/quadraticreject.py}
Start with an empty array of integers. Generate an integer \(0 \leq x
< n\), and check if \(x\) is already present in the array by iterating
through the array checking every element. If it is not present, append
it to the array. Repeat this process until the array is of the desired
length.

\subsection{Set-based rejection sampling}
\inputminted{Python}{code/rejectionsample.py}
As above, but use a data structure representing sets with an efficient membership test.
\cite{goodman}

\subsection{RANKSB}
\inputminted{Python}{code/ranksb.py}
Divide \(\NN_{<n}\) into \(k\) bins of nearly equal size. First
decide how many of the chosen values fall in each bin, by simulating
set-based rejection sampling while keeping only a count for each bin:
a draw is rejected with the probability that it would duplicate a value
already accepted in its bin, which depends only on that bin's count.
Then choose that many values within each bin; bins hold about one value
each, so a quadratic method suffices. The output is sorted, the expected
time is \(\bigO{k}\) for \(k \leq n/2\), and the program in
\cite[Chapter 4]{nijenhuiswilf} needs no storage beyond the output
array. Our C++ and Rust implementations follow that program, except
that they fill each bin as soon as they know where its values go,
rather than first marking out every bin's slots and then scanning for
the marks.

\subsection{Floyd's F2}
\inputminted{Python}{code/floydf2.py}
A twist on set-based rejection that uses compensatingly biased samples
to avoid multiple tests.
\cite{floydf2}
For random order output, our C++ and Rust implementations do not
shuffle afterwards. Instead, when the chosen value is already present,
they move a randomly chosen earlier output to the end and put the new
value in its place. This keeps the order uniformly random, and costs
an extra random number only on collisions.

\subsection{Quadratic F2}
\inputminted{Python}{code/quadraticf2.py}
Quadratic variant on Floyd's F2 which needs no external data
structure. Inspired by the implementation in \cite{rust-random} but
with some optimizations.

\subsection{Iterative choosing (Algorithm S)}
\inputminted{Python}{code/iterativechoose.py}
Iterate in order through each candidate to add to the list,
calculate for each the probability it should be part of the list given
the number of items added so far and the number remaining, and add
it with that probability.
\cite{taocp2}
\cite[Method 1, p.391]{fanetal}

\subsection{Reservoir sampling (Algorithm R)}
\inputminted{Python}{code/reservoirsample.py}
Initialize a \(k\)-element array with the elements of \(\NN_{<k}\)
in random order. Iterate over the elements of \(\NN_{<n} \setminus \NN_{<k}\),
and replace a random element of the array with each element with the
appropriate probability.
\cite{taocp2}

\subsection{Vitter's Algorithm D}
Like iterative choosing, produce the output in sorted order, but
instead of deciding about each value in turn, draw the number of values
to skip before the next chosen one directly. The skip has a known
discrete distribution, which Algorithm D samples by rejection from a
continuous approximation, the smallest of \(k\) uniform reals drawn in
one step as in \cite{bentleysaxe}, in \(\bigO{1}\) expected time per output, at
the cost of a few floating-point exponentiations. Once \(n \leq 13k\)
it falls back on Vitter's Algorithm A, which draws each skip in time
proportional to its length. Our implementation follows the code in the
paper's appendix.
\cite{vitterD}

\subsection{Hidden Shuffle}
\inputminted{Python}{code/hiddenshuffle.py}
Consider a Fisher-Yates shuffle of \(\NN_{<n}\) that stops after
\(k\) steps, so that the sample is whatever ends up in the first \(k\)
positions; call these the low positions, and the rest the high
positions. Each step reaches a high position independently, with known
probability, and which high position it reaches is uniform and
independent of everything else. So first count the steps that reach a
high position, then draw that many high positions with replacement in
sorted order as in \cite{bentleysaxe}. The first draw of a high position
adds its value to the sample; a repeat finds a low value swapped there
earlier, so the sample gains a low value instead, much as a collision in
Floyd's F2 adds a different value. Given their number, the low values
are a uniformly random subset of the low positions, chosen in order by
Vitter's Algorithm A. The output is sorted, the time is \(\bigO{k}\) in
the worst case, and no extra memory is needed; like Algorithm D, it
relies on floating-point arithmetic, with an exponentiation for each
high draw. \cite{hiddenshuffle}
The code printed in the paper can divide by zero, and its last step has
an off-by-one error that biases the output; our implementations apply
the corrections from the errata in \cite{sampleiterator}. We thank metasj
for bringing this algorithm to our attention.

\subsection{SELECT}
\inputminted{Python}{code/select.py}
Use a Fisher-Yates shuffle to randomize only the first \(k\) items of
an array of the elements of \(\NN_{<n}\). \cite{goodman}

\subsection{HSEL}
\inputminted{Python}{code/hsel.py}
As above, except that instead of allocating and initializing an
\(n\)-element array, we use a ``virtual'' array, with a hash table
storing only the modified elements.
\cite{hsel}
Our C++ and Rust implementations use a faster variant, which keeps the
first \(k\) entries of the virtual array in the output array itself,
so only swaps that reach beyond them touch the hash table. This variant
was described by rici \cite{rici}; we thank Mathias Weller for bringing
it to our attention.

\subsection{Cardchoose}
\inputminted{Python}{code/cardchoose.py}
Choose a multiset of \(k\) values below \(n - k + 1\) fairly, using
a P\'olya urn, then sort it and add each value's index to it to turn it
into a set. \autoref{starsandbars} to \autoref{proof} explain
why this works. The output is sorted, and the only storage needed is
the output array.

\section{Notation}

Let \(\NN_{<n} \defeq \{i \in \NN: i < n\}\), the set of natural
numbers less than \(n\) where \(\NN = \{0, 1, 2, \ldots\}\). Let
\(\binom{S}{k} \defeq \{s \subseteq S: |s| = k\}\), the set of all
\(k\)-element subsets of \(S\); note that \(\left|\binom{S}{k}\right|
= \binom{|S|}{k}\).

A \emph{multiset} is an extension of a set in which elements can
appear more than once; we use brackets to delimit the elements of a
multiset, so $[0, 1, 1]$ is the same multiset as $[1, 0, 1]$ but
distinct from $[0, 0, 1]$. Define \(\multichoose{U}{k}\) to be the set
of multisets of cardinality \(k\) whose elements are drawn from
\(U\), and \(\multichoose{n}{k} \defeq
\left|\multichoose{\NN_{<n}}{k}\right|\) the number of distinct
\(k\)-cardinality multisets over an \(n\)-element universe.

\section{Subsets as stars and bars}\label{starsandbars}

Write the numbers \(0, \ldots, n-1\) in a row, marking each chosen
number as a star and each unchosen one as a bar. For \(n = 7\), \(k =
3\) and the subset \(\{1, 2, 5\}\):

\begin{displaymath}
    \begin{array}{ c c c c c c c }
        0 & 1 & 2 & 3 & 4 & 5 & 6 \\
        \big| & \star & \star & \big| & \big| & \star & \big| \\
    \end{array}
\end{displaymath}

A row of \(k\) stars and \(n - k\) bars is exactly a \(k\)-element
subset of \(\NN_{<n}\): the stars' positions are the chosen numbers.
Following \cite[Chapter II \S 5]{feller}, instead of its position we describe each
star by its \emph{value}, the number of bars to its left:

\begin{displaymath}
    \begin{array}{ c c c c c c c }
        \big| & \star & \star & \big| & \big| & \star & \big| \\
          & 1 & 1 & & & 3 & \\
    \end{array}
\end{displaymath}

A value can be anything from \(0\) (before all the bars) to \(n - k\)
(after all of them), so there are \(t = n - k + 1\) possible values,
and stars can share a value when they sit in the same gap between
bars. The values of the stars therefore form a multiset in
\(\multichoose{\NN_{<t}}{k}\). This is a bijection between
\(\binom{\NN_{<n}}{k}\) and \(\multichoose{\NN_{<t}}{k}\). Going one
way, read off each star's value. Going back, the multiset says how
many stars have each value, that is, how many stars go in each gap,
and that rebuilds the row. The two directions undo each other, so
each subset corresponds to exactly one multiset and each multiset to
exactly one subset; in particular \(\multichoose{t}{k} =
\binom{t + k - 1}{k}\).

In code, the way back is: sort the multiset, then add each star's
index to its value, because a star's position is its bars to the left
plus its stars to the left:

\begin{displaymath}
    \begin{array}{ l c c c }
        \text{sorted values} & 1 & 1 & 3 \\
        \text{+ index} & 0 & 1 & 2 \\
        \text{positions} & 1 & 2 & 5 \\
    \end{array}
\end{displaymath}

That is the last three lines of the algorithm. Because the
correspondence is a bijection, choosing a multiset uniformly at
random and converting it gives a subset chosen uniformly at random:
each subset is reached from exactly one multiset. So what remains is
to choose an element of \(\multichoose{\NN_{<t}}{k}\) fairly.

\section{Choosing a multiset fairly}\label{fairmultiset}

Drawing \(k\) values independently from \(\NN_{<t}\) does not give a
uniform multiset. With \(t = 2\), \(k = 2\), the multiset \([0, 1]\)
comes up half the time, because it can arrive as \(0, 1\) or as \(1,
0\), while \([0, 0]\) and \([1, 1]\) get a quarter each. Independent
draws favour variety; we need to favour repeats, by exactly the right
amount.

Instead, build the row one star at a time, starting from the \(t -
1\) bars alone, and put each new star in a uniformly random gap of the
row so far. With \(i\) stars already placed, the row holds \(t - 1 +
i\) things, so it has \(t + i\) gaps. Name each gap by what is just to
its left:
\begin{itemize}
    \item The gap at the start of the row, and the gap just after each
    bar. There are \(t\) of these, and a star placed in the one after
    the \(b\)-th bar, or at the start for \(b = 0\), gets the value
    \(b\). This is a \emph{fresh} value.
    \item The gap just after each star. There are \(i\) of these, and a
    star placed in one sits in the same gap between bars as its left
    neighbour, so it gets the same value. This is a \emph{copy}.
\end{itemize}
For example, with \(t = 4\), so three bars, and two stars already
placed, \(d = [1, 3]\), there are six gaps, each marked \(\circ\) here
with the \(r\) that picks it above and the value it gives below:

\begin{displaymath}
    \begin{array}{ l c c c c c c c c c c c }
        r & 0 & & 1 & & 4 & & 2 & & 3 & & 5 \\
        \text{row} & \circ & \big| & \circ & \star_0 & \circ & \big| & \circ & \big| & \circ & \star_1 & \circ \\
        \text{value} & 0 & & 1 & & 1 & & 2 & & 3 & & 3 \\
    \end{array}
\end{displaymath}

That is the loop. \mintinline{python}{randrange(t + i)} picks a gap.
If \(r < t\), the new star takes the fresh value \(r\). Otherwise
\(r - t\) picks one of the stars already placed, and the new star
copies its value, \mintinline{python}{d[r - t]}. The list
\mintinline{python}{d} holds values in the order they were drawn, so
the copy is a single index lookup: one random number, one comparison
and one write per star, with no search.

A value that \(c\) stars already have owns \(c + 1\) gaps: one fresh
gap, and one after each of those stars. So a value drawn once is now
twice as likely as one never drawn, a value drawn twice three times as
likely, and so on. That is how repeats get favoured; the next section
shows it is by exactly the right amount.

\section{Proof}\label{proof}

Tag each star with the number of the draw that placed it. Different
values of \(r\) put the new star in different gaps, so a tagged row
records its whole history: remove the highest-tagged star, and its
left neighbour says which gap it went in, so whether it was fresh (a
bar, or nothing) or a copy (a star, and which one). Repeat to recover
every draw. So distinct sequences of draws produce distinct tagged
rows.

\autoref{sixruns} lists every possible run for \(t = 2\), \(k = 2\),
one bar and two stars. Every run has the same probability, \(\frac{1}{2}
\times \frac{1}{3}\), and the six results are the six tagged rows:
three ways to place two stars around a bar, times two ways to tag
them.

\begin{table}
    \begin{tabular}{ l l l l }
        first draw & row & second draw & row \\
        \hline
        \(r = 0\), fresh value 0 & \(\star_1 \,\big|\) & \(r = 0\), fresh value 0 & \(\star_2 \star_1 \,\big|\) \\
        & & \(r = 1\), fresh value 1 & \(\star_1 \,\big|\, \star_2\) \\
        & & \(r = 2\), copy \(\star_1\) & \(\star_1 \star_2 \,\big|\) \\
        \(r = 1\), fresh value 1 & \(\big|\, \star_1\) & \(r = 0\), fresh value 0 & \(\star_2 \,\big|\, \star_1\) \\
        & & \(r = 1\), fresh value 1 & \(\big|\, \star_2 \star_1\) \\
        & & \(r = 2\), copy \(\star_1\) & \(\big|\, \star_1 \star_2\) \\
    \end{tabular}
    \caption{Every run for \(t = 2\), \(k = 2\)}\label{sixruns}
\end{table}

In general there are \(t (t + 1) \cdots (t + k - 1) = \frac{(t + k -
1)!}{(t - 1)!}\) sequences of draws, each with probability
\(\frac{(t - 1)!}{(t + k - 1)!}\), and the same number of tagged
rows: \(\binom{t + k - 1}{k}\) ways to place the stars among the
bars, times \(k!\) ways to tag them. Since distinct sequences give
distinct tagged rows, every tagged row is produced by exactly one
sequence, and so every tagged row is equally likely. Each untagged
row has exactly \(k!\) taggings, so every untagged row is equally
likely, which is to say every multiset in
\(\multichoose{\NN_{<t}}{k}\), which is to say, by
\autoref{starsandbars}, every subset in \(\binom{\NN_{<n}}{k}\). In
\autoref{sixruns}, each of the three untagged rows is the result of
two runs, so each has probability \(\frac{1}{3}\).

\section{Prior art}\label{priorart}

Physicists have names for the three distributions in this story
\cite[Chapter II \S 5]{feller}. Distinguishable particles placed independently in
cells, the biased way of picking a multiset in \autoref{fairmultiset},
is Maxwell--Boltzmann statistics. Indistinguishable particles with every
occupancy pattern equally likely, a uniform multiset, is Bose--Einstein.
At most one particle per cell with every pattern equally likely, a
uniform subset, is Fermi--Dirac. Stars and bars is the standard way to
count the Bose--Einstein configurations, by matching them with
Fermi--Dirac ones. So the one-line summary of cardchoose is: generate
a Bose--Einstein configuration with a Pólya urn, then map it to
Fermi--Dirac by stars and bars.

The mathematics of both halves is classical. The multiset loop is a
Pólya urn \cite[Chapter V \S 2]{feller}: start with \(t\) balls, one of each
colour; draw a ball uniformly at random, and put it back along with a
new ball of the same colour. The urn is a textbook object of study, and
that with one ball of each colour its counts are uniform, which is to
say Bose--Einstein, is a standard lemma about it
\cite[Lemma 2.7]{levinperes}; Niven and Grendar \cite{nivengrendar} map
all three statistics onto the urn, with Maxwell--Boltzmann as
replacement without a copy, Bose--Einstein as replacement with a copy,
and Fermi--Dirac as no replacement. But the urn is presented as a model,
not as a way to generate anything, beyond passing remarks that it could
be used so \cite{cancriniposta}. The nearest thing to running an urn as
a sampler in earnest is in Bayesian statistics, where the
Blackwell--MacQueen urn \cite{blackwellmacqueen} draws an exchangeable
sequence from a Dirichlet process, which is a different purpose. The
combinatorial generation literature does generate random multisets, but
through stars and bars in the other direction: Nijenhuis and Wilf's
RANCOM \cite[Chapter 6]{nijenhuiswilf} chooses a random
\((k-1)\)-subset of \(\{1, \ldots, n+k-1\}\) and differences it. What
we have not found elsewhere is the urn presented as a generator for
uniform multisets, or its composition with stars and bars into a
sampler for sampling without replacement. Needing no set, map or extra
memory is not new in itself: Nijenhuis and Wilf's RANKSB
\cite[Chapter 4]{nijenhuiswilf} also uses nothing but the output
array, and so do Vitter's Algorithm D and, more recently, Shekelyan and
Cormode's Hidden Shuffle \cite{hiddenshuffle}, though they need
floating-point arithmetic where cardchoose and RANKSB use only exact
integer draws. We would be glad to hear of any earlier description of
cardchoose.

Sorted output without a sort has a classic answer for real numbers:
Bentley and Saxe \cite{bentleysaxe} generate \(k\) sorted uniform
reals in \(\bigO{k}\) time, drawing the largest as \(U^{1/k}\) and
repeating for the rest below it, and credit Friedman \cite{friedman}
with an essentially equivalent earlier program. This cannot stand in
for the urn: sorted independent draws, even rounded to integers, follow
the Maxwell--Boltzmann distribution over multisets, not the
Bose--Einstein one. Its closest analogue for distinct integers is
Vitter's Algorithm D, whose continuous approximation is the same step.

\section{Benchmarks}\label{benchmarks}

The accompanying repository
(\url{https://github.com/ciphergoth/sansreplace}) includes C++ and Rust
implementations of these algorithms, which were benchmarked for a
variety of values of \(n\) and \(k\), for both sorted output and
random output, on an Apple MacBook Pro:

\begin{itemize}
    \item CPU: Apple M4
    \item Cache: 128kiB L1 data and 16MiB L2 per performance core cluster
    \item Memory: 16GiB
    \item C++ compiler: clang 21.1, \verb|-O3|
    \item Rust compiler: rustc 1.98, release profile
\end{itemize}

We tested values of \(n\) and \(k\) that are Fibonacci numbers, with
\(n\) up to 701,408,733 (the 44th Fibonacci number) and \(k\) up to
102,334,155 (the 40th); larger \(k\) needs more memory than the test
machine has.

The C++ implementations use the standard library's
\mintinline{cpp}{std::unordered_set} and
\mintinline{cpp}{std::unordered_map}, which are node-based, and
\mintinline{cpp}{std::sort}, so they show the performance available
from the standard library. The Rust implementations use the Rust
standard library's \mintinline{rust}{HashSet} and
\mintinline{rust}{HashMap}, which are flat open-addressing hash tables
based on SwissTable, and its unstable sort. These are much faster: the
hash-based algorithms take about 0.4--0.5 times as long in Rust as in
C++, and cardchoose about 0.6--0.7 times as long, while RANKSB,
Vitter's Algorithm D and Hidden Shuffle, which need neither, take
about the same time in both languages.

In \autoref{cpprandomsmalln} to \autoref{rustsortedlargen} we graph

No algorithm is close to the fastest for all \(n, k\). Quadratic
rejection and quadratic F2 are the fastest for small \(k\), and SELECT,
reservoir sampling and iterative choosing for small \(n/k\), but each of
these is very slow elsewhere. The other algorithms run in
\(\bigO{k}\) or \(\bigO{k \log k}\) time, and differ by smaller
factors.

A ratio overstates differences where both times are small, so we also
measure how much each algorithm's time per number output exceeds that
of the fastest. By this measure three algorithms are never far from
the fastest: in every case, cardchoose, Hidden Shuffle and Algorithm D
are never more than 26\,ns per number slower, while every other
algorithm is at least 35\,ns slower somewhere, and most more than
100\,ns. Cardchoose is the simplest of the three: it is a few lines of
integer arithmetic, while the other two need floating point and are
considerably more involved: Algorithm D switches to Algorithm A once
\(n \leq 13k\), and Hidden Shuffle runs three stages in turn, the
last of them Algorithm A. Cardchoose's worst point in every case is at
the largest \(k\), with \(n\) the next Fibonacci number or so above
it, where the \(\bigO{n}\) algorithms are fastest; at \(k = n\) itself
it has almost nothing to do. Along those points its excess grows
slowly with \(k\), as the \(\log k\) factor of its sort would suggest.

For sorted output, the fastest of these is Hidden Shuffle in C++ and
cardchoose in Rust. Over the points with \(k \leq n/2\), Hidden Shuffle
is the faster of the two at 601 of 663 in C++, where cardchoose takes a
median of 1.68 times as long, and cardchoose at 406 of 663 in Rust,
where Hidden Shuffle takes a median of 1.09 times as long. Hidden
Shuffle takes about the same time in both languages, so the difference
is in cardchoose, most likely in its sort. Hidden Shuffle is also
faster than RANKSB at most of these points in both languages, with
RANKSB taking a median of 1.3 to 1.5 times as long. As \(k\)
approaches \(n\), RANKSB slows down, taking over 100 times
as long as the fastest algorithm at \(k = n\); \cite{nijenhuiswilf}
pairs it with iterative choosing (which Nijenhuis and Wilf refer to
as RKS2) for \(k \geq n/2\). Vitter's
Algorithm D, with its fallback to Algorithm A, has the smallest worst
case of any single algorithm for sorted output, but over all the
points tested takes a median of 1.3 times as long as cardchoose in C++
and 2.3 times as long in Rust.

For random output, the hash-based algorithms are competitive only with
a fast hash table. With C++ standard library hash tables, cardchoose is
faster than set-based rejection sampling, Floyd's F2 and HSEL at every
point with \(k \leq n/2\), and they take a median of about 1.65 times as
long, though Hidden Shuffle followed by a shuffle is faster still at
most of these points. With Rust's flat hash tables, HSEL is the fastest of
these four at most points, and cardchoose is never more than 1.51 times
slower than the fastest of them for \(k \leq n/2\). The hash-based
algorithms slow down at large \(k\), once the hash table no longer fits
in cache, and as \(k\) approaches \(n\). In theory, their
\(\bigO{k}\) performance compared to the \(\bigO{k \log k}\)
performance of cardchoose should mean that there is a value of \(k\)
at which they perform better. However, the poor cache coherence of
these algorithms means that their performance more closely resembles
\(\bigO{k \log k}\) in practice. For very large \(k\), a parallel
algorithm such as \cite{sandersetal} should generally be used; this
algorithm calls a sequential algorithm at the leaves of the parallel
tree it builds.

A good implementation will implement multiple algorithms, and choose
which one to use based on the values of \(n\) and \(k\).
\autoref{covertable} shows, for each language and order, the set of
one, two or three algorithms that comes closest to the fastest of all
of them at every point tested with \(k \geq 10\), if each point uses
the fastest algorithm in the set, together with the largest factor by
which that set is slower than the fastest. This assumes the best
choice is made at every point; an implementation has to choose by a
rule, such as a threshold on \(n/k\). Vitter's Algorithm D is itself
two algorithms, since it switches to Algorithm A once \(n \leq 13k\),
so wherever the best set includes it we also give the best set
without it.
