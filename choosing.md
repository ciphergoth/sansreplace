# Choosing algorithms

This page uses the [benchmark results](results.md).

## How the algorithms are scored

Each algorithm is scored by its worst time per number output, in each decade of _k_: for each band,
the most its time per call divided by _k_ reaches at any point with _k_ in the band, over every _n_
timed. That says what it costs at worst, in nanoseconds per number, for any _n_ and any _k_ in
that range. The bands run from _k_ = 10 to 100, 100 to 1,000 and so on, with the last from
10<sup>7</sup> to the largest _k_ timed; below 10, per-call overhead swamps everything. Each band
also has a floor: the score of choosing the fastest of all twelve algorithms separately at every
point, which no algorithm or set of algorithms can beat. I give worst cases rather than averages
because any average depends on which values of _n_ and _k_ I chose to test, and a band of _k_
rather than all of them because otherwise the largest _k_, where everything is slowest per number,
would decide every ranking.

The tables give, for each case and band, the best algorithm, along with any within 3% of it, which
is within the noise between runs, marked ≈; where any of those needs floating point (`hiddenshuffle` and
`vitterd`), the best algorithm that doesn't; then `cardchoose`, and the floor. Generated by
[`python/summarise`](python/summarise); [every algorithm's score in every band](results/latest/by-band.md)
is generated by `python/summarise --every-algorithm`. The quadratic algorithms, which went over the
time limit from _k_ = 1.3×10<sup>6</sup>, can't win a band where they weren't timed at every point.

Three algorithms are never far from the fastest per number output at any _k_: `hiddenshuffle`,
`vitterd` and `cardchoose` are never worse than 46 ns per number in any case, while every other
algorithm is worse than 100 ns per number somewhere it was timed. `cardchoose` is the simplest of
the three: it is a few lines of integer arithmetic, while the other two need floating point and are
considerably more involved. `vitterd` switches to Algorithm A once _n_ ≤ 13 _k_, and
`hiddenshuffle` runs three stages in turn, the last of them Algorithm A.

With sorted output, `cardchoose` is the best algorithm at every _k_ below 10<sup>7</sup> in Rust,
and `hiddenshuffle` above that; in C++, `cardchoose` is the best below 10<sup>4</sup>, tied with
`hiddenshuffle` up to 10<sup>6</sup>, and `hiddenshuffle` is the best above. `cardchoose` loses its lead in
C++ because libc++'s `std::sort` is slower than Rust's unstable sort; `hiddenshuffle` takes about
the same time in both. With random output, `quadraticf2` is the best for small _k_, below 1,000
in C++ and 100 in Rust, where it needs neither a sort nor a shuffle; in Rust, with its fast hash
tables, `hsel` is the best from there to 10<sup>6</sup>. Wherever the best algorithm needs floating
point, the best one that doesn't is `cardchoose`.

one. Seven algorithms are dominated by bands in every case, and `cardchoose` dominates all seven

`iterativechoose`, `reservoirsample` and `select` are among the fastest where _n_/_k_ is small,

## The best sets of algorithms

No single algorithm is the best at every _k_, so an implementation might implement several and
choose between them based on _n_ and _k_. For each case, the table gives the best set of one, two
or three algorithms, if each point uses the fastest algorithm in the set. A set's score in a band
is its worst time per number output there, and the table gives the most that exceeds the band's
floor, as a ratio, in the set's worst band: 1.00× means the set is as good as all twelve
algorithms together in every band. After each set comes the most it is slower than the best set of
three, in nanoseconds per number, in any band. Where the best set needs floating point
(`hiddenshuffle` or `vitterd`), the table also gives the best set that doesn't, or says that a
third such algorithm is no better than two. Ties between sets go to the one closer to the floor
over all the bands. This assumes the best choice is made at every point; an implementation has to
choose by a rule, such as thresholds on _k_ and _n_/_k_, and the region claims in the
[results](results.md) say where each algorithm wins. Generated by [`python/cover`](python/cover).

With sorted output, the best partner is `iterativechoose`, which wins where _k_ is a large fraction
of _n_; with random output, it is `quadraticf2`, which wins at small _k_. In C++, three algorithms
including `hiddenshuffle` are as good as all twelve together; in sorted order, no third integer-only
algorithm improves on the best integer-only pair.

## Implementing only Cardchoose

If you implement only one algorithm, `cardchoose` is a good choice. It is the best single
algorithm in three of the four cases; in the fourth, C++ with sorted output, only the two
floating-point algorithms beat it, because libc++'s `std::sort` is slower than Rust's. It is the
best integer-only algorithm in every case. Implemented alone, it is never more than 9–22 ns per
number slower than the best three algorithms together, in any case and at any _k_: 22 ns in C++
with random output, 19.5 ns in C++ with sorted output, 13.1 ns in Rust with random output and 8.8
ns in Rust with sorted output.

Its largest ratios to the floor are where calls are cheap. With random output, it is 3.66× the floor
in C++ and 2.42× in Rust for _k_ below 100, where `quadraticf2` needs neither a sort nor a shuffle,
but no call to `cardchoose` there takes more than 1.6 µs. With sorted output, it is 2.30× the floor
in C++ and 1.55× in Rust for _k_ ≥ 10<sup>7</sup>, where `hiddenshuffle` wins. In every case it is at least
as fast as some of the others at every point timed, and in Rust with sorted output, as fast as six
of the other eleven. It needs no storage beyond the output, and it is a few lines of integer
arithmetic.
